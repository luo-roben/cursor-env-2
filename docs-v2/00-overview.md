# 通用智能审查系统 — 总览

> 版本: v2.0 | 架构范式: LLM + RAG + ACE (Agentic Context Engineering) + Multi-Agent DAG
>
> 前置文档: v1.0 系列 (`docs/00-overview` ~ `docs/08-design-decisions`)，本文档为 v2 全面重构。

---

## 一、系统定位与核心理念

### 1.1 一句话定位

**通用智能审查平台：用 LLM 理解法规与模板，用 RAG 检索代替手动路由，用多智能体编排覆盖文本核对、红线检测、要素审查、语义合规、逻辑条款五大审查维度，构建一个"越用越准"、文档类型可无限扩展的智能审查引擎。**

### 1.2 与 v1 的本质区别

| 维度 | v1（智能合规审查系统） | v2（通用智能审查平台） |
|------|----------------------|----------------------|
| 审查对象 | 金融营销物料（海报、推文、说明书等） | **所有文档类型**：合同、营销物料、招募说明书，以及未来任意文档类型 |
| 问题模型 | 点状违规（某句话违规）+ 缺失元素 | **五大审查卡片**：文本核对 → 红线检测 → 要素审查 → 语义合规 → 逻辑条款 |
| 输出形态 | 违规点 + 原因 + 修改建议 | **分层修订建议**（tip / revision / negotiation_point）+ **字符级 span 定位** |
| 知识底座 | 法律法规 + 历史案例 | 法律法规 + **合同模板库** + **行业知识库** + 历史案例 |
| Agent 架构 | 单次 LLM 调用（长文档三 Agent 简述） | **StateGraph/DAG 显式编排**，7+ Agent 按文档类型动态组合 |
| 定位精度 | segment_index（段落级） | **char_offset_start / char_offset_end**（字符级 span） |
| 条款建模 | 无 | **条款层级识别**（条-款-项）+ 跨条款关系图谱 |

### 1.3 核心设计原则

| 序号 | 原则 | 说明 |
|------|------|------|
| P1 | **机器读法律/模板，人只做确认** | 法规、合同模板由 LLM 自动解析为结构化知识，人工仅 review & approve |
| P2 | **语义检索，不靠标签** | 审查时按内容语义从知识库检索相关法条/模板条款，不维护手动映射 |
| P3 | **每次审查动态组装上下文** | ACE 架构：根据文档类型、行业、渠道，实时检索法条 + 模板 + 案例组装 prompt |
| P4 | **越用越准** | 每次人工复核沉淀为新案例，持续增强知识库 |
| P5 | **可溯源** | 每条审查结论附法条/模板原文引用，可追溯、可审计 |
| P6 | **简单自定义** | 企业用自然语言描述审查要求，零技术门槛 |
| P7 | **条款级精度** | 合同等长文档支持条款层级建模、跨条款一致性检查、字符级定位 |
| P8 | **文档类型可扩展** | 新增文档类型只需注册类型描述 + 配置审查卡片组合，不改代码、不改流程 |

## 二、新旧方案对比

### 2.1 传统方案 vs v1 vs v2

```
❌ 传统方案（Drools/正则驱动）:
法律法规文本 → 人工阅读 → 人工总结规则 → 人工写 DRL/正则 → 人工维护标签映射
               ↑ 几百部法律、几千条法条，人工根本写不完，也维护不了

✅ v1 方案（LLM + RAG，仅营销物料）:
法律法规文本 → LLM 自动解析 → 结构化知识入库 → 审查时 LLM 基于检索到的知识做判断
               ↑ 解决了法规解析问题，但仅支持营销物料、不支持合同/长文档

✅✅ v2 方案（通用智能审查平台）:
法规 + 合同模板 + 行业知识 → LLM 自动解析 → 多模态知识存储
→ 审查时 StateGraph 编排多 Agent → 五维审查卡片 → 字符级定位 + 分层修订建议
               ↑ 通用化、条款级精度、多 Agent 协作、文档类型可扩展
```

### 2.2 关键差异

| 维度 | 传统方案 | v1 方案 | v2 方案 |
|------|---------|---------|---------|
| 法规解读 | 人工阅读，人工总结规则 | LLM 自动解析，人工确认 | 同 v1，增加合同模板解析 |
| 规则维护 | 手动编写 DRL/正则 | 无需手动规则 | 无需手动规则，模板库自动匹配 |
| 内容路由 | 人工维护映射表 | 语义检索自动匹配 | 语义检索 + 文档类型注册表路由 |
| 支持文档类型 | 固定，改代码才能加 | 营销物料为主 | **任意文档类型**，注册即可用 |
| 合同审查 | 不支持 | 不支持 | **原生支持**：条款解析、跨条款分析、修订建议 |
| 定位精度 | 无 | 段落级 (segment_index) | **字符级** (char_offset) |
| 修订建议 | 无 | 自由文本 suggestion | **分层建议**：tip / revision / negotiation_point |
| Agent 编排 | 无 | 单次 LLM（三 Agent 简述） | **StateGraph/DAG 显式编排** |
| 成本控制 | 无 LLM 成本 | 无缓存策略 | **Prompt 缓存 + 模型路由 + token 分桶** |

## 三、五大审查卡片体系

v2 将所有审查能力归类为 **5 大卡片**，每种文档类型按需组合卡片，形成差异化审查流水线。

### 3.1 卡片总览

```

### 3.2 卡片详细说明

| 卡片 | 审查焦点 | 覆盖的问题类型 | 底层模块 | 适用文档 |
|------|---------|-------------|---------|---------|
| ① 文本基础核对 (Text & Basics) | 文字层面的低级错误 | 错别字、标点误用、数字错误、格式不规范（字号/对齐/分段）、OCR 识别误差 | NLP 纠错引擎 + 规则校验器 | 所有文档 |
| ② 红线与敏感词 (Redlines) | 绝对禁止的用词/表述 | 政治敏感词、绝对化用语（"最好"/"第一"/"保证"）、行业违禁词、广告法极限词 | Aho-Corasick 自动机 + 语义扩展匹配 | 所有文档 |
| ③ 形式与要素审查 (Format & Elements) | 必备组成元素是否齐全 | 合同：缺签署日期/盖章/附件/必备条款；营销：缺风险提示/基金全称/管理人名称；招募说明书：缺法定章节 | ComplianceChecklist（自检清单）+ 布局分析器 | 所有文档（清单按类型差异化） |
| ④ 语义与合规审查 (Semantic Compliance) | 内容是否违反法规/模板规范 | 误导性宣传、隐含保本承诺、业绩披露不完整、与标准模板条款实质性偏离、监管红线违反 | **RAG + LLM**（核心审查能力） | 所有文档 |
| ⑤ 逻辑与条款审查 (Logic & Clauses) | 条款间的逻辑一致性 | 跨条款矛盾（权利 vs 义务不对等）、定义条款与使用不一致、交叉引用断裂（"依照第 8.3 条"但无 8.3 条）、生效/终止条款冲突 | **条款图谱 Agent + 跨条款一致性 Agent** | 合同、招募说明书等长文档 |

### 3.3 文档类型与卡片组合矩阵

不同文档类型启用不同的卡片组合：

| 文档类型 | ① 文本核对 | ② 红线检测 | ③ 要素审查 | ④ 语义合规 | ⑤ 逻辑条款 |
|---------|:---------:|:---------:|:---------:|:---------:|:---------:|
| 营销海报/推文 | ✅ | ✅ | ✅ | ✅ | — |
| 基金招募说明书 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 合同（各类型） | ✅ | ✅ | ✅ | ✅ | ✅ |
| 直播话术脚本 | ✅ | ✅ | — | ✅ | — |
| 内部制度文件 | ✅ | ✅ | ✅ | ✅ | — |
| **新增文档类型 X** | 注册时配置 | 注册时配置 | 注册时配置 | 注册时配置 | 注册时配置 |

> **扩展性说明**：新增文档类型时，在文档类型注册表中配置该类型启用哪些卡片即可。每张卡片的审查逻辑是通用的，差异化通过知识库内容（法条/模板/清单）体现。

### 4.1 第一层：知识构建层（离线/准实时）

**目标：让机器读懂法律、理解合同模板、积累行业知识。**

- **法规采集与解析**：同 v1，通过爬虫 / RSS / 人工导入采集法规原文，LLM 按"条-款-项"拆分并结构化。
- **合同模板库构建**（v2 新增）：采集行业标准合同模板（采购、NDA、SaaS、劳务、股权等），按条款层级解析，标注每个条款的角色（定义条款 / 权利条款 / 义务条款 / 违约条款 / 争议解决条款），生成条款级 Embedding 用于模板匹配。
- **行业知识库构建**（v2 新增）：沉淀行业特定的合同规范、审查最佳实践、常见风险模式（如"劳动合同中竞业限制条款的合理期限"）。
- **人工确认**：同 v1，LLM 解析结果经人工确认工作台审核后发布。
- **多模态存储**：PostgreSQL（结构化）+ Milvus（向量）+ Elasticsearch（全文）+ Neo4j（知识图谱，Phase 3 引入）。
- **历史案例导入**：同 v1，但扩展为支持合同审查案例的结构化导入。

详见：[01-knowledge-layer.md](01-knowledge-layer.md)

### 4.2 第二层：审查执行层（在线）

**目标：StateGraph 编排多 Agent，五卡片覆盖全审查维度。**

- **文档类型识别**：自动识别或用户选择文档类型（合同 / 营销物料 / 招募说明书等）。
- **卡片组合选择**：根据文档类型从注册表加载启用的审查卡片组合。
- **条款解析 Agent**（v2 新增，合同/长文档专用）：识别条款层级结构（条-款-项），提取定义条款，构建文档内条款引用图。
- **文本核对 Agent**（卡片①）：NLP 纠错 + 格式校验。
- **红线检测 Agent**（卡片②）：Aho-Corasick 匹配 + 语义扩展敏感词检测。
- **要素审查 Agent**（卡片③）：按文档类型加载 ComplianceChecklist，逐项检查必备要素。
- **语义合规 Agent**（卡片④，核心）：ACE 上下文动态组装（法条 + 模板 + 案例检索）→ LLM 审查。
- **逻辑条款 Agent**（卡片⑤，v2 新增）：基于条款解析结果，检查跨条款一致性、权责对等性、交叉引用完整性。
- **终审汇总 Agent**：合并所有卡片结果，去重，生成统一审查报告。
- **后处理**：法条 ID 回填（防幻觉）、风险评分、字符级 span 校验。

详见：`02-review-engine.md`（待编写）

### 4.3 第三层：进化学习层（持续）

**目标：越用越准 + 案例生命周期管理。**

- **人工复核**：同 v1，审查结果进入复核队列。
- **案例沉淀**：同 v1，但新增合同审查案例的结构化（含条款 ID、修订建议类型等）。
- **案例生命周期管理**（v2 新增，回应 Gemini 评估 R3）：
  - 时间衰减：案例权重随时间指数衰减，半衰期 12 个月。
  - 邻域去重：同一 Embedding 邻域下 confirmed 案例超过阈值时，抽样保留代表性案例。
  - 定期审计：与黄金测试集联动，法条失效时自动标记关联案例。
- **黄金测试集**：同 v1（增强5），每周自动回归，漂移监控。
- **知识库增强**：新沉淀的案例可被后续审查检索，形成正循环。

详见：`03-feedback-loop.md`（待编写）

## 五、文档类型扩展性模型

### 5.1 文档类型注册表

v2 引入 `doc_type_registry`（文档类型注册表），新增文档类型无需改代码：

```
┌──────────────────────────────────────────────────────────────────────┐
│  文档类型注册表 (doc_type_registry)                                    │
│                                                                      │
│  注册一种新文档类型只需定义:                                            │
│                                                                      │
│  {                                                                   │
│    "doc_type_id": "labor_contract",                                  │

## 七、多 Agent StateGraph 编排（概述）

### 7.1 编排架构

v2 使用 **StateGraph（有向无环图）** 替代 v1 的"单次 LLM 调用 + 三 Agent 简述"：

```
┌──────────────────────────────────────────────────────────────────┐
│  StateGraph: 合同审查流水线 (contract_full_review)                 │
│                                                                   │
│  START                                                            │
│    │                                                              │
│    ▼                                                              │
│  [文档解析 & 类型识别] ─────────────────────────────────────┐    │
│    │                                                        │    │
│    ▼                                                        │    │
│  [条款解析 Agent] ← 条款层级识别、定义抽取、引用图构建       │    │
│    │                                                        │    │
│    ├──── 并行分支 ────────────────────────────────┐         │    │
│    │                                              │         │    │
│    ▼                                              ▼         │    │
│  [文本核对 Agent ①]                     [红线检测 Agent ②]   │    │
│    │                                              │         │    │
│    └──────────────┬───────────────────────────────┘         │    │
│                   ▼                                          │    │
│  [要素审查 Agent ③] ← 加载 ComplianceChecklist              │    │
│    │                                                        │    │
│    ▼                                                        │    │
│  [语义合规 Agent ④] ← ACE 上下文组装 + LLM 审查             │    │
│    │                                                        │    │
│    ▼ (仅当 clause_parsing_enabled = true)                   │    │
│  [逻辑条款 Agent ⑤] ← 跨条款一致性检查                      │    │
│    │                                                        │    │
│    ▼                                                        │    │
│  [终审汇总 Agent] ← 合并所有卡片结果、去重、生成报告         │    │
│    │                                                        │    │
│    ▼                                                        │    │
│  [后处理] ← 法条 ID 回填、span 校验、评分计算                │    │
│    │                                                        │    │
│    ▼                                                        │    │
│  END → 返回结果 + 进入复核队列                               │    │
└──────────────────────────────────────────────────────────────────┘
```

### 7.2 StateGraph 的优势（相比 v1 的单次调用）

| 维度 | v1（单次 LLM 调用） | v2（StateGraph 编排） |
|------|--------------------|--------------------|
| 复杂度管理 | 所有审查逻辑塞进一个 prompt | 每个 Agent 职责单一，prompt 更短更精确 |
| 并行能力 | 无 | 卡片①②可并行，显著降低总延迟 |
| 错误隔离 | 一个 Agent 失败整体失败 | 单个 Agent 失败不影响其他卡片出结果 |
| 模型路由 | 统一用一个模型 | 不同 Agent 可用不同模型（轻量级卡片用 4o-mini） |
| 可观测性 | 黑盒 | 每个 Agent 有独立的日志/指标/耗时追踪 |
| 扩展性 | 加审查维度需改 prompt | 加审查维度只需新增 Agent 节点 |

### 7.3 模型路由策略

| Agent | 推荐模型 | 理由 |
|-------|---------|------|
| 条款解析 Agent | GPT-4o-mini / DeepSeek-V3 | 结构化任务，不需要深度推理 |
| 文本核对 Agent ① | 本地 NLP 模型 | 纠错不需要大模型 |
| 红线检测 Agent ② | 无 LLM（纯规则） | Aho-Corasick 自动机 |
| 要素审查 Agent ③ | GPT-4o-mini | 清单检查，任务简单 |
| 语义合规 Agent ④ | **GPT-4o / Claude Sonnet** | 核心审查，需要最强推理能力 |
| 逻辑条款 Agent ⑤ | **GPT-4o / Claude Sonnet** | 跨条款推理，需要长上下文能力 |
| 终审汇总 Agent | GPT-4o-mini | 合并/去重，不需要深度推理 |

**成本优化效果**：将非核心 Agent 路由到低成本模型，核心审查 Agent 使用高质量模型。预估可节省 40-60% 的 LLM 调用成本。

## 八、成本控制与性能优化

### 8.1 Prompt 缓存（回应 Gemini 评估 R2）

```
┌──────────────────────────────────────────────────────────────────┐
│  Prompt 缓存策略                                                   │
│                                                                   │
│  背景: 同类型文档的审查，System Prompt（法条上下文）高度重叠         │
│                                                                   │
│  策略1: LLM Provider 级缓存                                       │
│  · Anthropic: prompt_caching（β），相同前缀自动缓存                │
│  · OpenAI: predicted_outputs，缓存 system + few-shot 部分          │
│  · 效果: 减少 ~50% 的 input token 计费                             │
│                                                                   │
│  策略2: 应用层法条摘要缓存                                         │
│  · 法条知识更新后预生成压缩摘要（~40 tokens/条）                    │
│  · 缓存 {doc_type + product_type} → 法条摘要组合                   │
│  · 审查时直接取缓存的摘要组装 prompt，跳过检索+压缩步骤              │
│  · Redis 缓存，TTL = 1 小时（法条更新时主动失效）                   │
│                                                                   │
│  策略3: Embedding 缓存                                             │
│  · 同一段文本的 Embedding 结果缓存 24 小时                          │
│  · 批量审查同一文档的多个版本时，未修改段落直接复用向量              │
└──────────────────────────────────────────────────────────────────┘
```

### 8.2 Token 预算分桶（回应 Gemini 评估 R4）

v1 的 token 裁剪是全局 top-K，可能把某一类法条全部裁掉。v2 改为**按 norm_type 分桶裁剪**：

```
Token 预算分桶策略:

  法条上下文总预算: 6000 tokens

  按 norm_type 分桶:
  ┌──────────────┬───────────────┬──────────────────────────┐
  │ 桶 (norm_type)│ 预算比例       │ 说明                     │
  ├──────────────┼───────────────┼──────────────────────────┤
  │ 禁止          │ 35% = 2100t  │ "不得做什么"，核心违规依据 │
  │ 义务          │ 25% = 1500t  │ "应当做什么"，缺失项依据   │
  │ 定义          │ 15% = 900t   │ 术语定义，辅助理解         │
  │ 权利          │ 10% = 600t   │ "可以做什么"，边界参考     │
  │ 程序          │ 10% = 600t   │ 流程性规定                │
  │ 预留          │ 5% = 300t    │ 合同模板条款 / 其他        │
  └──────────────┴───────────────┴──────────────────────────┘

  每个桶内部按 RRF 得分排序，桶满时裁掉低分法条。
  效果: 每种类型的法条至少保留 top-N，不会被其他类型挤出。
```

## 九、合同类型差异化

### 9.1 合同分类体系

| 大类 | 具体类型 | 审查侧重 | 典型风险点 |
|------|---------|---------|----------|
| 销售合同 | 商品销售合同、设备采购合同 | 验收条款、质量标准、付款条件 | 验收标准模糊、付款节奏不合理 |
| 服务合同 | SaaS 服务协议、咨询服务合同 | SLA 条款、知识产权归属、保密义务 | SLA 承诺过高、知产归属不清 |
| 劳动合同 | 劳动合同、劳务派遣合同 | 竞业限制、试用期、解除条件 | 竞业限制过宽、违约金过高 |
| 保密协议 | NDA、保密承诺函 | 保密范围、保密期限、违约责任 | 保密范围过宽、期限过长 |
| 股权合同 | 股权转让协议、投资协议 | 对赌条款、回购权、一票否决 | 对赌条件不合理、退出机制缺失 |
| 租赁合同 | 房屋租赁、设备租赁 | 租期、押金、维修责任 | 提前解约条件苛刻 |
| 金融合同 | 基金合同、信托合同 | 风险揭示、投资限制、费率结构 | 风险提示不充分、费率隐藏 |

### 9.2 合同类型对审查流水线的影响

不同合同类型会影响：
- **模板匹配**：使用对应类型的标准合同模板集
- **ComplianceChecklist**：加载对应类型的必备条款清单
- **语义合规的 RAG 检索**：过滤到对应类型的法条子集
- **逻辑条款审查的侧重**：如劳动合同侧重竞业限制对等性，股权合同侧重对赌条款合理性

## 十、常见技术问题（FAQ）

### Q1: v2 的多 Agent 编排会不会比 v1 单次调用更慢？

**不会。** 核心原因：

1. **并行能力**：卡片①②可并行，卡片③④⑤可串行或并行（取决于依赖关系）。v1 是串行的一次大调用。
2. **模型路由**：非核心 Agent 使用轻量模型（4o-mini，延迟 ~1s），只有核心 Agent 使用大模型（4o，延迟 ~5-8s）。
3. **Prompt 更短**：每个 Agent 的 prompt 只包含该卡片需要的上下文，不是全部塞进一个 prompt。

典型延迟对比：

| 场景 | v1 延迟 | v2 延迟 |
|------|---------|---------|
| 营销海报（短文本） | 8-15s | 6-10s |
| 合同（1万字） | 不支持 | 20-40s |
| 招募说明书（3万字） | 30-60s | 25-45s |

### Q2: 字符级定位的准确率如何保证？

**三层保障机制：**

1. **LLM 输出 matched_text**：要求 LLM 输出精确的原文子串。
2. **后处理 span 校验**：用 `matched_text` 在原文中做子串匹配，计算精确的 `char_offset_start` / `char_offset_end`。如果匹配失败，降级为段落级定位。
3. **span 漂移处理**：如果文档被编辑后重新审查，用 `matched_text` 重新锚定位置（re-anchoring），而不依赖绝对偏移量。

### Q3: 案例库会不会无限膨胀？（回应 Gemini R3）

**不会。** v2 引入案例生命周期管理：

1. **时间衰减**：案例权重按指数衰减，半衰期 12 个月。超过 24 个月的案例权重降至 ~0.25，在检索中几乎不被召回。
2. **邻域去重**：同一 Embedding 邻域（余弦相似度 > 0.95）下，如果 confirmed 案例超过 10 条，只保留学习价值分最高的 5 条，其余归档。
3. **法条失效联动**：法条标记 deprecated 时，关联案例自动降权。
4. **硬上限**：每个租户的活跃案例上限 50,000 条，超出后触发归档。

### Q4: 合同模板库从哪里来？

**三个来源：**

1. **公开标准模板**：从法律数据库（北大法宝、威科先行）采集行业标准合同模板，人工审核后入库。
2. **企业内部模板**：企业上传自有的标准合同模板，系统自动解析条款结构并标注。
3. **审查沉淀**：经过多次审查和人工复核的高质量合同，经脱敏后可沉淀为参考模板。

初始阶段目标：每个合同类型 10-20 份标准模板，总计 100-200 份。

### Q5: token 预算分桶会不会导致某些桶利用率很低？

**会，但这是正确的 trade-off。** 桶预算是上限而非固定分配。当某个桶的法条数量不足以填满预算时，剩余 token 自动回流到"预留"桶，分配给其他超额的桶。只有在所有桶都满的极端情况下，分桶才会真正限制某些类型的法条数量。

### Q6: v2 的检索延迟预算是多少？（回应 Gemini R1）

采纳 Gemini 的建议，调整为更现实的延迟预算：

| 指标 | v1 预算 | v2 预算（修正） |
|------|---------|----------------|
| 五路检索 p50 | < 500ms | < 600ms |
| 五路检索 p95 | < 500ms | **< 1500ms** |
| 单次向量检索 | 未定义 | < 100ms |
| 结构化查询 | 未定义 | < 50ms |
| 知识图谱查询 | 未定义 | < 300ms（Phase 3 引入后） |
