### 2.2 单条复核操作 (确认/驳回/修改/补充)

对于 LLM 给出的每一条判定，人工复核人员可以执行以下操作。这四种操作与 v1 保持一致：

```
┌─────────────────────────────────────────────────────────────────────┐
│  复核操作详情                                                        │
│                                                                      │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  复核人操作选项:                                               │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ① 确认 (Confirm)                                     │    │  │
│  │  │   "同意 LLM 的判定"                                   │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 审查结果标记为 human_confirmed = true            │    │  │
│  │  │     · 生成一条新案例: verdict 与 LLM 一致              │    │  │
│  │  │     · 案例入库，可被后续审查检索                        │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ② 驳回 (Reject)                                      │    │  │
│  │  │   "不同意 LLM 的判定"                                  │    │  │
│  │  │   → 必填: 驳回理由                                    │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 审查结果标记为 human_rejected = true             │    │  │
│  │  │     · 生成纠错案例 (高价值，检索权重 +20%)             │    │  │
│  │  │     · 案例入库，帮助 LLM 在相似场景做出正确判断         │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ③ 修改 (Modify)                                      │    │  │
│  │  │   "部分同意，但需要调整判定内容"                        │    │  │
│  │  │   → 可修改: 严重程度 / 法条引用 / 修改建议 / 违规理由  │    │  │
│  │  │   → v2 新增可修改: suggestion_type (tip/revision/     │    │  │
│  │  │                    negotiation_point)                  │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 保存修改后的版本                                 │    │  │
│  │  │     · 生成修正案例: 保留原始 LLM 判定 + 人工修正版     │    │  │
│  │  │     · 两个版本都入库，供系统学习"应该调整的方向"        │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ④ 补充 (Supplement)                                   │    │  │
│  │  │   "LLM 漏检了，这段内容还有其他问题"                   │    │  │
│  │  │   → 人工添加 LLM 未发现的问题                          │    │  │
│  │  │   → 必填: 问题描述 / 法条引用 / 建议                   │    │  │
│  │  │   → v2 新增必填: suggestion_type                      │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 生成漏检案例 (最高价值)                           │    │  │
│  │  │     · 标记 source=human_supplement                    │    │  │
│  │  │     · 案例入库后，相似内容的检索优先级提高              │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  通用选项:                                                     │  │
│  │  · 添加复核备注 (自由文本)                                     │  │
│  │  · 关联相似案例 (手动链接)                                     │  │
│  │  · 标记为"典型案例" (加入教学库)                                │  │
│  └───────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
```

## 3. 合同修订联动 (v2 新增)

### 3.1 设计动机

在合同审查场景中，人工复核不仅仅是"确认/驳回 LLM 判定"，还经常涉及**直接修改合同条款**。这带来了一个 v1 未处理的核心问题：

> **当人工修改了合同的某个条款后，LLM 对该条款的原有审查标注是否仍然有效？**

例如：
1. LLM 标注"第7.1条——甲方免责条款过于宽泛"（severity: critical）
2. 人工将第7.1条修改为"甲方就其过错行为承担相应赔偿责任"
3. 此时 LLM 的原有标注已经**不再适用于修改后的文本**

如果不处理这个问题，会导致：
- 审查报告中的标注与实际合同文本不一致
- 修改后的条款可能引入新的风险，但未被检测
- 修订历史无法追溯

### 3.2 修订触发的标注失效

```
┌──────────────────────────────────────────────────────────────────────┐
│  合同修订 → 标注失效逻辑                                               │
│                                                                      │
│  触发条件:                                                           │
│    人工在审查工作台中编辑了合同条款的文本内容                           │
│    (通过内嵌编辑器 或 通过 OnlyOffice/Word 回写)                      │
│                                                                      │
│  失效判定:                                                           │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  对每个被修改的条款 (clause_id):                                │ │
│  │                                                                │ │
│  │  1. 计算文本变更率:                                             │ │
│  │     change_ratio = editDistance(old_text, new_text)             │ │
│  │                    / max(len(old_text), len(new_text))          │ │
│  │                                                                │ │
│  │  2. 失效规则:                                                   │ │
│  │     if change_ratio > 0.1 (变更超过10%):                       │ │
│  │       → 该条款上的所有 AI 标注标记为 INVALIDATED                │ │
│  │       → 触发重新审查流程                                       │ │
│  │                                                                │ │
│  │     if change_ratio <= 0.1 (微小修改, 如错别字修正):            │ │
│  │       → AI 标注保留，但标记为 STALE (待确认)                   │ │
│  │       → 在审查报告中提示"该条款已有微小修改"                    │ │
│  │                                                                │ │
│  │  3. 关联条款传播:                                               │ │
│  │     if 被修改的条款被其他条款引用:                               │ │
│  │       → 引用方的 AI 标注也标记为 STALE                         │ │
│  │       例: 修改了第2.2条(价款), 第8.1条引用了"按第2.2条约定"     │ │
│  │           → 第8.1条的 AI 标注也标记为 STALE                    │ │
│  │                                                                │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  标注状态:                                                           │
│  ┌──────────────┬─────────────────────────────────────────────┐     │
│  │ 状态          │ 含义                                        │     │
│  │ ACTIVE        │ 当前有效的 AI 标注                          │     │
│  │ INVALIDATED   │ 因条款修改而失效，需重新审查                 │     │
│  │ STALE         │ 条款有微小修改或被引用条款修改，待确认       │     │
│  │ SUPERSEDED    │ 已被重新审查的新标注替代                    │     │
│  └──────────────┴─────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.3 受影响卡片的重新审查

```
┌──────────────────────────────────────────────────────────────────────┐
│  重新审查流程                                                         │
│                                                                      │
│  当条款标注被标记为 INVALIDATED 后:                                    │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  Step 1: 确认重新审查范围                                      │ │
│  │                                                                │ │
│  │  系统自动提示:                                                  │ │
│  │  ┌──────────────────────────────────────────────────────────┐ │ │
│  │  │ ⚠️ 第7.1条已被修改，以下审查卡片的标注已失效:              │ │ │
│  │  │                                                          │ │ │
│  │  │  ☑ COMPLIANCE 卡片 — "甲方免责条款过于宽泛" (critical)   │ │ │
│  │  │  ☑ RISK 卡片 — "责任限制可能导致乙方权益受损" (major)    │ │ │
│  │  │  ☑ SUGGESTION 卡片 — 修订建议 (已由人工执行)             │ │ │
│  │  │                                                          │ │ │
│  │  │  是否对修改后的条款重新运行审查？                          │ │ │
│  │  │  [✅ 重新审查选中卡片] [⏭️ 跳过，手动确认] [🔄 全部重审] │ │ │
│  │  └──────────────────────────────────────────────────────────┘ │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  Step 2: 执行增量审查                                          │ │
│  │                                                                │ │
│  │  仅对修改后的条款文本重新运行:                                  │ │
│  │    · ACE 上下文检索 (用新文本做向量检索)                        │ │
│  │    · LLM 审查 (新文本 + 检索到的法条/案例)                     │ │
│  │    · 后处理 (引用校验 + 评分)                                  │ │
│  │                                                                │ │
│  │  LLM prompt 中包含修订上下文:                                   │ │
│  │    "以下条款经过人工修订:                                       │ │
│  │     原文: '甲方不承担任何责任'                                  │ │
│  │     修订后: '甲方就其过错行为承担相应赔偿责任'                  │ │
│  │     请审查修订后的版本是否合规"                                 │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  Step 3: 合并审查结果                                          │ │
│  │                                                                │ │
│  │  · 新审查结果替换失效的标注 (旧标注状态改为 SUPERSEDED)         │ │
│  │  · 未受影响的条款保留原有标注                                   │ │
│  │  · 重新计算整体 risk_score                                     │ │
│  │  · 更新审查报告                                                │ │
│  │                                                                │ │
│  │  结果可能:                                                     │ │
│  │  a) 修订解决了问题 → 新标注: compliant → 风险评分下降         │ │
│  │  b) 修订未完全解决 → 新标注: needs_review → 需继续复核        │ │
│  │  c) 修订引入新问题 → 新标注: violation → 需重新修改           │ │
│  └────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

## 5. 案例在审查中的使用

```
案例在审查中的作用 — 合同场景示例:

  用户提交审查: 一份服务合同中的条款
  "甲方对因本服务造成的任何间接损失不承担赔偿责任"

    → 向量检索案例库:

    命中案例 CASE-2026-00023456:
      文档类型: 服务合同
      原文: "甲方不承担任何责任"
      判定: violation (人工确认)
      理由: 免除己方全部责任的条款可能被认定无效
      修订: "甲方就其过错行为承担相应赔偿责任"
      修订后判定: compliant

    命中案例 CASE-2026-00023500:
      文档类型: 采购合同
      原文: "卖方对产品的间接损失免责"
      判定: compliant (人工确认)
      理由: 间接损失免责属于合理的商业风险分配

    → 两条案例放入 LLM 的 prompt:
    LLM 看到:
    - "不承担任何责任" → 违规（免除全部责任）
    - "间接损失免责" → 合规（合理的风险分配）
    - 当前要审查: "间接损失不承担赔偿"

    LLM 的判断更精准:
    "间接损失不承担赔偿" 更接近案例2的模式，
    属于合理的间接损失免责约定，应判定为合规，
    但建议明确"间接损失"的定义范围。

案例在审查中的作用 — 营销场景示例:

  用户提交: "该基金亏损风险较低"

    → 向量检索案例库:

    命中案例 CASE-2026-00012345:
      原文: "亏损概率很小"
      判定: violation (人工确认)
      理由: 构成暗示保本

    命中案例 CASE-2026-00012400:
      原文: "本基金属于中低风险产品"
      判定: compliant (人工确认)
      理由: 客观描述产品风险等级

    → LLM 判断更精准:
    "亏损风险较低" 更接近 "亏损概率很小" 的表述模式,
    构成对风险的弱化暗示，应判定为违规。
```

## 8. 审核人一致性监控 (v2 新增)

### 8.1 设计动机

在 v1 中，案例沉淀依赖人工复核的质量，但没有检测**不同审核人对相同模式的判定是否一致**。这会导致：

- 审核人 A 认为"间接损失免责"合规，审核人 B 认为违规 → 沉淀的案例互相矛盾
- LLM 学习到矛盾案例后，判定结果不稳定
- 随时间推移，案例库中的噪声越来越多，"越用越准"闭环退化为"越用越乱"

因此 v2 引入审核人一致性监控，检测跨审核人的判定差异，并通过校准机制保证案例质量。

### 8.2 一致性度量方法

```
┌──────────────────────────────────────────────────────────────────────┐
│  审核人一致性度量                                                      │
│                                                                      │
│  方法: Cohen's Kappa (κ) 系数                                        │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  Cohen's Kappa 计算:                                           │ │
│  │                                                                │ │
│  │  κ = (P_o - P_e) / (1 - P_e)                                  │ │
│  │                                                                │ │
│  │  P_o = 观察到的一致率 (两个审核人判定一致的比例)                │ │
│  │  P_e = 预期的偶然一致率 (随机情况下一致的概率)                  │ │
│  │                                                                │ │
│  │  κ 值解读:                                                     │ │
│  │  ┌─────────────────────────────────────────────┐              │ │
│  │  │ κ 范围        一致性水平     系统判定          │              │ │
│  │  │ ──────────────────────────────────────────── │              │ │
│  │  │ 0.81 - 1.00   几乎完全一致   ✅ 优秀          │              │ │
│  │  │ 0.61 - 0.80   高度一致       ✅ 良好          │              │ │
│  │  │ 0.41 - 0.60   中度一致       ⚠️ 需关注        │              │ │
│  │  │ 0.21 - 0.40   低度一致       ❌ 需校准        │              │ │
│  │  │ < 0.20        几乎不一致     ❌ 需紧急校准    │              │ │
│  │  └─────────────────────────────────────────────┘              │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  数据采集方式:                                                       │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  方式1: 自然重叠                                               │ │
│  │    同一条审查结果碰巧被两个不同审核人复核                       │ │
│  │    (例如交接班、离职交接等场景)                                 │ │
│  │                                                                │ │
│  │  方式2: 定期校准抽样 (推荐)                                    │ │
│  │    系统每周随机抽取 20 条已完成复核的审查结果                   │ │
│  │    分配给另一位审核人进行"盲审"(不显示原审核人的判定)           │ │
│  │    比较两次判定的一致性                                         │ │
│  │                                                                │ │
│  │  方式3: 争议样本重审                                           │ │
│  │    当系统检测到同一违规模式的 AI 判定准确率波动时              │ │
│  │    回溯对应案例，分配给多位审核人独立判定                       │ │
│  └────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

### 8.3 不一致检测与预警

```
┌──────────────────────────────────────────────────────────────────────┐
│  不一致检测引擎                                                       │
│                                                                      │
│  检测维度:                                                           │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  维度1: 判定方向不一致                                          │ │
│  │                                                                │ │
│  │  审核人 A 对内容 X: 确认违规 (confirm violation)               │ │
│  │  审核人 B 对相似内容 X': 驳回违规 (reject → compliant)         │ │
│  │                                                                │ │
│  │  检测方法:                                                      │ │
│  │  1. 对所有已审案例做聚类 (基于审查内容的 Embedding)              │ │
│  │  2. 在同一聚类中，如果不同审核人的 verdict 存在矛盾             │ │
│  │     → 触发 "判定方向冲突" 预警                                  │ │
│  │  3. 冲突案例进入仲裁队列 (P0+ 优先级)                          │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  维度2: 严重程度不一致                                          │ │
│  │                                                                │ │
│  │  审核人 A 对某类问题: 通常修改为 critical                      │ │
│  │  审核人 B 对同类问题: 通常修改为 minor                         │ │
│  │                                                                │ │
│  │  检测方法:                                                      │ │
│  │  1. 按违规类型 (issue_type) 分组                               │ │
│  │  2. 计算每个审核人在该类型下的 severity 分布                   │ │
│  │  3. 如果两位审核人的分布显著不同 (卡方检验 p < 0.05)           │ │
│  │     → 触发 "严重程度偏差" 预警                                  │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  维度3: 建议类型不一致 (v2 特有)                                │ │
│  │                                                                │ │
│  │  审核人 A: 将某类建议分类为 REVISION (可直接采纳修订)          │ │
│  │  审核人 B: 将同类建议分类为 NEGOTIATION_POINT (需协商)         │ │
│  │                                                                │ │
│  │  检测方法:                                                      │ │
│  │  1. 按条款类型分组                                              │ │
│  │  2. 比较不同审核人的 suggestion_type 分布                      │ │
│  │  3. 差异显著时触发预警                                          │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  预警输出:                                                           │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  预警邮件示例:                                                  │ │
│  │                                                                │ │
│  │  ⚠️ 审核人一致性预警                                           │ │
│  │                                                                │ │
│  │  检测到以下不一致:                                              │ │
│  │                                                                │ │
│  │  1. [判定方向冲突] 合同免责条款审查                             │ │
│  │     审核人张三: 12 次判定中 10 次确认违规 (83%)                │ │
│  │     审核人李四: 15 次判定中 6 次确认违规 (40%)                  │ │
│  │     Cohen's κ = 0.35 (低度一致)                                │ │
│  │     → 建议安排校准会议                                         │ │
│  │                                                                │ │
│  │  2. [严重程度偏差] 业绩展示合规审查                             │ │
│  │     审核人张三: 平均 severity = major                          │ │
│  │     审核人王五: 平均 severity = minor                          │ │
│  │     → 建议统一评判标准                                         │ │
│  │                                                                │ │
│  │  受影响案例: 27 条 → 已进入仲裁队列                            │ │
│  └────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

### 8.4 校准机制

```
┌──────────────────────────────────────────────────────────────────────┐
│  审核人校准机制                                                       │
│                                                                      │

│  │                                                                │ │
│  │  流程:                                                          │ │
│  │  1. 系统自动选取 10 条"高争议"案例                              │ │
│  │     (同一模式下不同审核人判定差异最大的案例)                     │ │
│  │  2. 所有审核人独立重新判定 (盲审，不看他人结果)                 │ │
│  │  3. 展示判定结果差异，团队讨论统一标准                          │ │
│  │  4. 形成"判定标准备忘录"，输入系统作为审核指引                  │ │
│  │  5. 被讨论确定的案例标记为"校准案例"，学习价值分 +2            │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  机制2: 仲裁队列                                                │ │
│  │                                                                │ │
│  │  当系统检测到同一模式下两位审核人判定矛盾时:                    │ │
│  │  1. 相关案例自动进入仲裁队列                                    │ │
│  │  2. 分配给第三位高级审核人 (仲裁者)                             │ │
│  │  3. 仲裁者的判定作为最终判定                                    │ │
│  │  4. 原有两条矛盾案例的学习价值分归零                            │ │
│  │  5. 仲裁结果生成新的"仲裁案例"，学习价值分 +3                  │ │
│  │                                                                │ │
│  │  仲裁者选择规则:                                                │ │
│  │  · 不是原两位审核人中的任何一位                                  │ │
│  │  · 优先选择在该文档类型/违规类型上准确率最高的审核人             │ │
│  │  · 如果无可用审核人，升级到合规负责人                            │ │

│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  机制3: 个人偏差校正                                            │ │
│  │                                                                │ │
│  │  系统持续跟踪每位审核人的判定偏差:                               │ │
│  │                                                                │ │
│  │  ┌──────────────────────────────────────────────────────────┐ │ │
│  │  │  审核人画像:                                              │ │ │
│  │  │                                                          │ │ │
│  │  │  审核人: 张三                                             │ │ │

│  │  │  修改率: 8%                                               │ │ │

│  │  │  偏差方向: 偏宽松 (tendency: lenient)                     │ │ │

│  │  │  建议: 在"合同免责条款"审查中，对该审核人的判定          │ │ │

│  │  └──────────────────────────────────────────────────────────┘ │ │
```
