## 一、合同审查 vs 营销审查：本质差异

### 1.1 为什么合同审查是一个独立的问题域

营销材料审查的核心是**逐段合规判定**——每句话独立判断是否违反某条法规。合同审查的核心是**跨条款逻辑推理**——第 3 条的定义影响第 8 条的违约责任解读，第 5 条的权利必须在第 6 条有对等义务。

这不是"同一个引擎 + 不同法条"就能解决的。是完全不同的问题模型。

### 1.2 关键差异对比

| 维度 | 营销材料审查 | 合同审查 |
|------|------------|---------|
| 审查对象 | 短文本/图片/推文，通常 < 5000 字 | 合同全文，通常 5000-50000 字 |
| 违规粒度 | **点状**：某一句话违规 | **条款级 + 跨条款**：一条条款有风险，或多条条款矛盾 |
| 上下文依赖 | 低：每段可独立判断 | 高：定义条款影响全文理解，前后条款必须一致 |
| 法条依据 | 明确：广告法、基金销售管理办法等 | 模糊：合同法原理 + 行业惯例 + 模板标准 |
| 输出要求 | 违规点 + 原因 + 建议 | **可直接采纳的修订文本** + **精确到字符的定位** |
| 客户判断标准 | 合规官说 OK 即可 | 法务和业务双方都要认"可采纳"；定位错一个字符都会被投诉 |
| 知识底座 | 法条知识库 | 法条 + **行业标准合同模板库** + 历史审查案例 |
| 核心失败模式 | 漏检、过度审查 | **修订不可执行**、**定位对不上**、**跨条款矛盾被遗漏** |

### 1.3 合同审查的 5 层挑战

```
┌─────────────────────────────────────────────────────────────────┐
│  合同审查的 5 层挑战                                              │
│                                                                  │
│  Layer 1: 结构理解                                               │
│  · 合同不是"段落列表"，是"条款树"                                │
│  · 必须识别第X条Y款Z项的层级结构                                 │
│  · 必须理解定义条款的作用域                                      │
│  · 必须发现交叉引用（"依照本合同第8.3条"）                       │
│                                                                  │
│  Layer 2: 语义理解                                               │
│  · 同一个词在不同条款可能有不同含义                               │
│  · 定义条款限定了术语的特定含义                                  │
│  · "合理"、"及时"、"必要"等模糊表述需要行业标准对标              │
│                                                                  │
│  Layer 3: 逻辑推理                                               │
│  · 权利 vs 义务的对称性检查                                      │
│  · 违约责任 vs 免责条款的自洽性                                  │
│  · 终止条件 vs 生效条件的完整性                                  │
│  · 金额/比例在多个条款中的一致性                                 │
│                                                                  │
│  Layer 4: 精确定位                                               │
│  · LLM 说"第8.3条有问题"，必须精确到这条的字符位置               │
│  · 定位必须映射到 Word/OnlyOffice 的书签坐标                     │
│  · 合同修改后，原有定位必须重新锚定                               │
│                                                                  │
│  Layer 5: 高质量修订                                             │
│  · 修订必须符合法律语言规范                                      │
│  · 修订必须是最小改动（不能重写整段）                             │
│  · 修订不能引入新的逻辑矛盾                                     │
│  · 有些问题没有"标准答案"，只能给谈判建议                        │
└─────────────────────────────────────────────────────────────────┘
```

## 二、合同条款解析器详细设计

### 2.1 总体架构

合同条款解析器是 StateGraph 合同审查流中的**第一个 Agent 节点**，其输出是后续所有合同审查步骤的基础。

```
┌─────────────────────────────────────────────────────────────────┐
│  ContractClauseParser — 合同条款解析器                             │
│                                                                  │
│  输入: 合同全文 (纯文本 / Word 解析后文本)                        │
│  输出:                                                           │
│    · clause_tree: 条款层级树                                     │
│    · definitions: 定义条款列表                                   │
│    · cross_references: 交叉引用列表                              │
│    · parties: 当事方列表                                         │
│    · positioning_data: 各条款的字符偏移量                         │
│                                                                  │
│  实现: LLM 调用(结构识别) + 正则辅助(编号提取) + 后处理(校验)     │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 条款层级识别（第X条Y款Z项）

合同条款的编号体系复杂且不统一，解析器必须兼容多种格式：

```
支持的编号格式:

  格式A（中文法律体）:
    第一条  合同目的
      第一款  甲方应当...
        （一）具体事项1
        （二）具体事项2

  格式B（数字阿拉伯体）:
    1. 合同目的
      1.1 甲方应当...
        1.1.1 具体事项1
        1.1.2 具体事项2

  格式C（混合体）:
    第一条  合同目的
      1.1 甲方应当...
      1.2 乙方应当...

  格式D（无编号，仅标题分段）:
    【合同目的】
    甲方应当...
```

**解析策略：LLM + 正则混合**

```
┌─────────────────────────────────────────────────────────────────┐
│  条款层级解析流程                                                  │
│                                                                  │
│  Step 1: 正则预处理 — 提取候选条款边界                            │
│                                                                  │
│  正则模式集:                                                     │
│  · /^第[一二三四五六七八九十百]+条\s*/gm         → 一级条款       │
│  · /^第[一二三四五六七八九十]+款\s*/gm           → 二级款        │
│  · /^（[一二三四五六七八九十]+）/gm              → 三级项        │
│  · /^(\d+)\.\s+/gm                              → 一级(数字)    │
│  · /^(\d+\.\d+)\s+/gm                           → 二级(数字)    │
│  · /^(\d+\.\d+\.\d+)\s+/gm                      → 三级(数字)    │
│  · /^【[^】]+】/gm                               → 标题分段      │
│                                                                  │
│  输出: 候选条款列表，每条含:                                     │
│    · clause_number: 编号文本                                     │
│    · char_offset: 在原文中的字符偏移                              │
│    · raw_text: 从该编号到下一个编号之间的文本                     │
│                                                                  │
│  Step 2: LLM 结构化验证与增强                                    │
│                                                                  │
│  Prompt:                                                         │
│  "请验证以下合同条款的层级结构，并补充以下信息:                   │
│   1. 每条条款的标题(如有)                                        │
│   2. 条款类型: definition/obligation/right/liability/             │
│      termination/dispute/general                                 │
│   3. 如果正则解析的层级有误，请纠正                               │
│   4. 如果有遗漏的条款边界，请补充                                │
│                                                                  │
│   当前正则解析结果:                                               │
│   {regex_parsed_clauses_json}"                                   │
│                                                                  │
│  Step 3: 后处理校验                                              │
│  · 编号连续性检查（第一条→第二条→...不应跳号）                    │
│  · 层级嵌套合理性检查（二级必须在一级内）                        │
│  · 字符偏移量与原文对齐校验                                      │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 定义条款提取

定义条款是合同理解的基础——"本合同所称'关联方'指……"这类条款定义了合同中特定术语的含义。

```
┌─────────────────────────────────────────────────────────────────┐
│  定义条款提取                                                      │
│                                                                  │
│  识别规则（正则 + LLM）:                                         │
│                                                                  │
│  正则模式:                                                       │
│  · /本合同[所中]称[的""]([^""]+)[""]/g                           │
│  · /["""]([^""]+)[""]是指/g                                      │
│  · /以下[简称统称合称][为""]([^""]+)/g                           │
│                                                                  │
│  输出结构:                                                       │
│  {                                                               │
│    "definitions": [                                              │
│      {                                                           │
│        "term": "关联方",                                         │
│        "definition_text": "与甲方存在控股关系...",                │
│        "source_clause": "1.2",                                   │
│        "char_offset": 890,                                       │
│        "char_length": 120,                                       │
│        "usage_clauses": ["3.1", "5.4", "8.2"]                   │
│      }                                                           │
│    ]                                                             │
│  }                                                               │
│                                                                  │
│  LLM 增强:                                                       │
│  · 正则无法捕获的隐式定义（如"前述约定的质量标准"）               │
│  · 定义的使用位置扫描（在全文中搜索定义术语出现的所有位置）       │

```

### 2.4 交叉引用检测

合同条款之间的引用关系是条款图谱的关键边。

```
┌─────────────────────────────────────────────────────────────────┐
│  交叉引用检测                                                      │
│                                                                  │
│  正则模式:                                                       │
│  · /依照本合同第?(\d+[\.\d]*)[条款项]/g                          │

│  · /违反(?:本合同)?第?(\d+[\.\d]*)[条款]/g                       │
│                                                                  │
│  输出结构:                                                       │
│  {                                                               │
│    "cross_references": [                                         │
│      {                                                           │
│        "source_clause": "5.1",                                   │
│        "target_clause": "8.3",                                   │
│        "reference_text": "依照本合同第8.3条",                     │
│        "reference_type": "depends_on",                           │

│                                                                  │

│  · depends_on  — "依照/根据/按照第X条" — 执行依赖               │
│  · refers_to   — "参见第X条" — 参考关系                         │
│  · violates    — "违反第X条" — 违约触发关系                     │
│  · overrides   — "第X条另有约定的除外" — 覆盖关系               │

│  校验: 检查 target_clause 是否真实存在于条款树中                  │
```

## 三、合同内部条款图谱

### 3.1 图谱结构

合同内部条款图谱用于表示一份合同中条款之间的关系。这不同于法律知识图谱（法条间的关系），这是**单份合同内部的结构化表示**。

```
图谱节点 (Clause Node):
┌───────────────────────────────────────────────────────────────┐
│  ClauseNode                                                    │
│  · clause_number: "8.3"                                       │
│  · clause_title: "违约责任"                                    │
│  · clause_type: liability                                     │
│  · clause_text: "如甲方未按第5.1条规定..."                     │
│  · char_offset: 12450                                         │
│  · char_length: 356                                           │
│  · party_mentions: ["甲方", "乙方"]                           │
│  · key_amounts: ["合同金额的30%"]                              │
│  · key_dates: ["签约后30日内"]                                 │
└───────────────────────────────────────────────────────────────┘

图谱边 (Clause Edge):
┌───────────────────────────────────────────────────────────────┐
│  edge_type        说明                     示例               │
│  ─────────────────────────────────────────────────────────── │
│  REFERENCES       引用关系                 8.3 引用 5.1       │
│  DEFINES          定义使用关系             3.1 使用 1.2定义   │
│  DEPENDS_ON       执行依赖                 5.1 依赖 2.3       │
│  OVERRIDES        覆盖关系                 9.2 覆盖 8.1       │
│  VIOLATES         违约触发                 5.1违反→触发8.3    │
│  SYMMETRIC_TO     权责对称                 5.1(甲方权利)↔6.1  │
│  CONTRADICTS      逻辑矛盾（审查发现）     5.1 与 7.2 矛盾    │
└───────────────────────────────────────────────────────────────┘
```

### 3.2 PG 递归 CTE 实现（Phase 1-2）

```sql
-- 条款节点表
CREATE TABLE contract_clause_node (
    id          BIGSERIAL PRIMARY KEY,
    task_id     BIGINT NOT NULL REFERENCES review_task(id),
    clause_number VARCHAR(50) NOT NULL,
    clause_title  VARCHAR(200),
    clause_type   VARCHAR(50),  -- definition/obligation/right/...
    clause_text   TEXT,
    char_offset   INT,
    char_length   INT,
    party_mentions JSONB,  -- ["甲方", "乙方"]
    key_amounts    JSONB,  -- ["合同金额的30%"]
    key_dates      JSONB,  -- ["签约后30日内"]
    UNIQUE(task_id, clause_number)
);

-- 条款边表
CREATE TABLE contract_clause_edge (
    id          BIGSERIAL PRIMARY KEY,
    task_id     BIGINT NOT NULL REFERENCES review_task(id),
    source_clause VARCHAR(50) NOT NULL,
    target_clause VARCHAR(50) NOT NULL,
    edge_type     VARCHAR(50) NOT NULL,  -- references/defines/depends_on/...
    evidence_text VARCHAR(500),  -- 引用原文，如"依照本合同第8.3条"
    char_offset   INT,
    char_length   INT
);

-- 查询某条款的所有关联条款（2跳以内）
WITH RECURSIVE clause_graph AS (
    SELECT source_clause, target_clause, edge_type, 1 AS depth
    FROM contract_clause_edge
    WHERE task_id = :task_id AND source_clause = :clause_number
  UNION ALL
    SELECT e.source_clause, e.target_clause, e.edge_type, cg.depth + 1
    FROM contract_clause_edge e
    JOIN clause_graph cg ON e.source_clause = cg.target_clause
    WHERE e.task_id = :task_id AND cg.depth < 2
)
SELECT DISTINCT source_clause, target_clause, edge_type, depth
FROM clause_graph
ORDER BY depth, source_clause;
```

## 四、跨条款一致性分析

跨条款一致性分析是审查卡片 ⑤ 的核心能力，由 **跨条款一致性 Agent** 执行。

### 4.1 权利 vs 义务对称性检查

```
┌─────────────────────────────────────────────────────────────────┐
│  权利义务对称性检查                                                │
│                                                                  │
│  原理: 合同中甲方的权利通常对应乙方的义务，反之亦然。              │
│  如果权利没有对应义务，说明合同不平衡。                            │
│                                                                  │
│  检查逻辑:                                                       │
│  1. 从条款图谱中提取所有 clause_type=right 的条款                │
│  2. 对每条权利条款，检查是否存在对应的义务条款:                   │
│     · 甲方权利 → 乙方是否有对等义务?                             │
│     · 乙方权利 → 甲方是否有对等义务?                             │
│  3. 对等判断由 LLM 执行（语义层面的对称性）                      │
│                                                                  │
│  LLM Prompt:                                                    │
│  "请分析以下合同条款的权利义务对称性:                              │
│                                                                  │
│   甲方权利条款:                                                  │
│   第5.1条: 甲方有权在乙方违约时解除合同                           │
│                                                                  │
│   请检查合同中是否有与之对称的乙方权利:                           │
```

## 五、字符级定位（span）详细设计

### 5.1 为什么字符级定位是合同审查的刚需

```
段落级定位（v1）:
  "第3段违规" → 用户需要自己在原文中找到第3段 → 体验差

字符级定位（v2）:
  "第8.3条'违约金为合同金额的30%'有风险"
  → 用户点击 → Word/OnlyOffice 自动跳转并高亮这 12 个字 → 体验好

  如果定位对不上 → 用户信任塌方 → 系统被弃用

  这不是"锦上添花"，是合同审查产品的生死线。
```

### 5.2 LLM 输出设计

```
LLM 审查 prompt 中增加要求:
"对每条发现的问题，请输出 exact_substring 字段——
 该字段必须是合同原文中能找到的、包含问题的最短连续文本片段。
 exact_substring 必须是原文的精确子串，不可改写。"

LLM 输出示例:
{
  "issues": [
    {
      "clause_number": "8.3",
      "issue_type": "excessive_penalty",
      "severity": "major",
      "description": "违约金比例30%显著高于行业惯例",
      "exact_substring": "违约金为合同金额的30%",
      "suggestion_type": "negotiation_point",
      "suggestion": "建议降低至10-20%"
    }
  ]
}
```

### 5.3 后端定位流程

```
┌─────────────────────────────────────────────────────────────────┐
│  字符级定位 — 三级回退策略                                         │
│                                                                  │
│  输入: LLM 输出的 exact_substring                                │
│  目标: 找到该文本在合同原文中的 (char_offset, char_length)       │
│                                                                  │
│  Level 1: 严格子串搜索                                           │
│                                                                  │
│    result = contractFullText.indexOf(exactSubstring)             │
│    if (result >= 0) {                                            │
│      char_offset = result                                        │
│      char_length = exactSubstring.length()                       │
│      confidence = "exact"                                        │
│      → 成功 ✅                                                   │
│    }                                                             │
│                                                                  │
│  Level 2: 模糊子串搜索 (容忍空白/标点差异)                       │
│                                                                  │
│    normalizedSubstring = normalize(exactSubstring)               │
│    normalizedContract = normalize(contractFullText)              │
│    // normalize: 去除多余空白、统一标点（全角→半角）              │
│    result = normalizedContract.indexOf(normalizedSubstring)      │
│    if (result >= 0) {                                            │
│      // 映射回原文的 char_offset                                 │
│      char_offset = mapToOriginalOffset(result)                   │
│      confidence = "fuzzy"                                        │
│      → 成功 ⚠️                                                  │
│    }                                                             │
│                                                                  │
│  Level 3: 段落级回退                                             │
│                                                                  │
│    // 根据 clause_number 定位到对应条款                           │
│    clauseNode = clauseGraph.findByNumber("8.3")                  │
│    if (clauseNode != null) {                                     │
│      char_offset = clauseNode.charOffset                         │
│      char_length = clauseNode.charLength                         │
│      confidence = "clause_level"                                 │
│      → 降级成功 ⚠️⚠️                                            │
│    }                                                             │
│                                                                  │
│  Level 4: 定位失败                                               │
│    confidence = "unlocated"                                      │
│    → 审查结果仍保留，标记为"定位未确认"                           │
│    → 提升人工复核优先级                                          │
│                                                                  │
│  定位成功率目标:                                                 │
│    Level 1 (精确):  > 85%                                       │
│    Level 1+2 (含模糊): > 95%                                    │
│    Level 1+2+3 (含段落回退): > 99%                               │
└─────────────────────────────────────────────────────────────────┘
```

### 5.4 合同修改后的重新锚定（Re-anchoring）

```
┌─────────────────────────────────────────────────────────────────┐
│  Re-anchoring — 合同修改后的定位重新锚定                          │
│                                                                  │
│  场景: 用户在 Word/OnlyOffice 中修改了合同文本后，                │
│  原有的 char_offset 可能全部失效。                                │
│                                                                  │
│  策略: 不重新跑 LLM，用文本 diff 算法重新计算偏移                 │
│                                                                  │
│  流程:                                                           │
│  1. 用户修改合同文本后，上传新版本                                │
│  2. 系统对新旧版本做字符级 diff (Myers diff 算法)                │
│  3. 基于 diff 结果，重新计算每个 span 的新偏移量:                │
│                                                                  │
│     原始: "...违约金为合同金额的30%..." (offset=12450)           │
│     修改: 在 offset=5000 处插入了 200 个字符                     │
│     新 offset = 12450 + 200 = 12650                              │
│                                                                  │
│  4. 验证: 在新文本的新 offset 处提取 char_length 个字符            │
│     如果与原始 exact_substring 匹配 → 锚定成功                   │
│     如果不匹配 → 重新执行 Level 1-3 定位                         │
│                                                                  │
│  5. 如果原始文本被修改（用户采纳了修订建议）:                     │
│     该 span 标记为 "已修复"                                      │
│     对应的 review_result 标记为 resolved                          │
│                                                                  │
│  性能: diff + re-anchoring 在 50000 字合同上 < 100ms             │
└─────────────────────────────────────────────────────────────────┘
```

### 5.5 与 Word/OnlyOffice 书签的集成

```
集成方式:

  方案A: OOXML 书签注入 (Word .docx)
  · 在 .docx 的 XML 结构中，在 char_offset 位置插入
    <w:bookmarkStart> 和 <w:bookmarkEnd> 标签
  · 书签名: review_{task_id}_{result_id}
  · 用户在 Word 中可通过书签导航直接跳转

  方案B: OnlyOffice Plugin API
  · 通过 OnlyOffice Document Server 的 JavaScript Plugin API
  · 调用 Api.GetDocument().GetRange(offset, offset+length)
  · 设置高亮样式: range.SetHighlight("yellow")
  · 添加批注: range.AddComment(description)

  方案C: PDF 标注 (针对 PDF 合同)
  · 使用 Apache PDFBox 在对应位置添加高亮注释
  · 注释内容 = issue description + suggestion
```

### 6.2 生成 Diff 卡片

```
对齐结果 → 生成两类审查卡片:

  1. "缺失条款" 卡片 (归入卡片③ 形式与要素审查):
     · 条款名称: "交货方式"
     · 模板基准: 标准采购合同模板 v2.1, 第4条
     · 严重程度: major (标准模板中为必备条款)
     · 建议: "建议参照标准模板增加交货方式条款，明确交货时间、

  2. "偏离条款" 卡片 (归入卡片⑤ 逻辑与条款审查):
     · 条款: "5. 独家经销"
     · 偏离类型: 待审合同新增了标准模板中没有的条款

             是否有必要，以及独家范围、期限是否合理"

  3. "内容偏离" 卡片 (归入卡片⑤):
     · 条款: "6. 违约责任"
     · 偏离: 待审合同的违约金比例(30%)高于模板(15%)
     · 建议类型: negotiation_point
```

### 6.3 LCS 对齐算法

```
条款级对齐使用 LCS (Longest Common Subsequence) 变体:

  输入:
    模板条款标题序列 T = ["合同目的", "标的物", "价款", "交货", ...]
    合同条款标题序列 C = ["合同目的", "标的物描述", "合同价款", ...]

  相似度函数:
    sim(t, c) = cosine_similarity(embed(t), embed(c))
    如果 sim > 0.8 → 视为匹配

  算法:
    dp[i][j] = max(dp[i-1][j], dp[i][j-1],
                   dp[i-1][j-1] + (sim(T[i], C[j]) > 0.8 ? 1 : 0))

  输出:
    matched_pairs: [(T[0], C[0]), (T[1], C[1]), ...]
    missing_in_contract: [T[3], T[7], ...]  → 缺失条款
    extra_in_contract: [C[4], ...]           → 新增条款
```

## 七、修订建议质量保障

### 7.1 suggestion_type 分类

详见 08-design-decisions.md 增强 7。三种类型：

| 类型 | 适用场景 | 要求 |
|------|---------|------|
| tip | 提示性建议 | 无格式要求，自由文本 |
| revision | 可直接采纳的修订 | 最小改动原则 + diff 校验 + 跨条款影响检查 |
| negotiation_point | 协商要点 | 风险说明 + 行业惯例 + 协商方向 |

### 7.2 修订 diff 校验（revision 类型）

```
┌─────────────────────────────────────────────────────────────────┐
│  修订 Diff 校验流程                                                │
│                                                                  │
│  输入:                                                           │
│    · original_text: 原始条款文本                                 │
│    · revised_text: LLM 生成的修订文本                            │
│                                                                  │
│  校验 1: 最小改动原则                                            │
│    edit_distance = levenshtein(original_text, revised_text)      │
│    change_ratio = edit_distance / original_text.length()         │
│    if (change_ratio > 0.5) {                                     │
│      → 拒绝修订: "改动幅度过大，请缩小修改范围"                  │
│      → 降级为 suggestion_type = tip                              │
│    }                                                             │
│                                                                  │
│  校验 2: 禁用词检查                                              │
│    quickFilter.checkBannedWords(revised_text)                    │
│    if (hasBannedWords) {                                         │
│      → 拒绝修订: "修订文本包含禁用词"                            │
│      → 标记为需人工修改                                          │
│    }                                                             │
│                                                                  │
│  校验 3: 金额/日期一致性                                         │
│    if (revised_text contains amounts or dates) {                 │
│      otherClauses = clauseGraph.getRelatedClauses(clause_number) │
│      for (clause : otherClauses) {                               │
│        if (inconsistentAmounts(revised_text, clause.text)) {     │
│          → 警告: "修订后的金额与第X条不一致"                     │
│        }                                                         │
│      }                                                           │
│    }                                                             │
│                                                                  │
│  校验 4: 语法完整性                                              │
│    · 修订文本是否是完整句子（有主语谓语）                        │
│    · 标点是否正确配对                                            │
│    · 法律专业术语是否使用正确                                    │
│                                                                  │
│  校验通过 → 标记为 validated_revision                             │
│  校验失败 → 降级为 tip 或标记为 needs_human_edit                 │
└─────────────────────────────────────────────────────────────────┘
```

### 7.3 跨条款影响检查

```
┌─────────────────────────────────────────────────────────────────┐
│  跨条款影响检查                                                    │
│                                                                  │
│  场景: 修订第5.1条的文本后，可能影响引用了第5.1条的其他条款       │
│                                                                  │
│  流程:                                                           │
│  1. 从条款图谱中查询: 哪些条款引用了当前被修订的条款              │
│     SELECT target_clause FROM contract_clause_edge               │
│     WHERE source_clause IN (                                     │
│       SELECT source_clause FROM contract_clause_edge             │
│       WHERE target_clause = :modified_clause                     │
│     ) AND task_id = :task_id                                     │
│                                                                  │
│  2. 对每个关联条款，用 LLM 检查修订是否引入新矛盾:               │
│     Prompt:                                                      │
│     "第5.1条已被修订为: {revised_text}                            │
│      请检查以下引用了第5.1条的条款是否受到影响:                   │
│      · 第8.3条: {clause_8_3_text}                                │
│      · 第9.1条: {clause_9_1_text}                                │
│      如果修订导致了新的矛盾或不一致，请指出。"                    │
│                                                                  │
│  3. 如果发现新矛盾:                                              │
│     · 修订建议中增加警告: "注意：本条修订可能影响第8.3条"         │
│     · 建议同时修订受影响的条款                                   │
│     · UI 上以关联线连接受影响的条款                               │
│                                                                  │
│  4. 如果无影响:                                                  │
│     · 修订标记为 no_side_effects                                 │
│     · 用户可放心采纳                                             │
└─────────────────────────────────────────────────────────────────┘
```

## 八、端到端合同审查 Walkthrough

### 场景

用户上传一份 PDF 格式的采购合同（约 15000 字，30 条条款），选择合同类型"采购合同"。

### Step 1: 内容解析 (~2s)

```
输入: 采购合同 PDF (15页)

处理:
  1. Apache Tika 提取 PDF 文本
  2. 保留章节结构（标题、缩进、编号）
  3. 元数据提取: document_type=contract, 15000字

输出:
  全文纯文本 + 元数据
  {
    document_type: "contract",
    content_type: "采购合同",
    contract_type: "purchase",
    total_chars: 15000,
    total_pages: 15
  }
```

### Step 2: 合同类型识别 (~200ms)

```
基于关键词 + LLM 轻量分类:
  "采购"、"买受人"、"标的物"、"交货" → purchase 类型
  置信度: 0.95
```

### Step 3: 条款解析 (~5s)

```
ContractClauseParser 执行:

  正则预处理:
    识别到 30 个候选条款边界
    编号格式: 混合体（第一条~第三十条 + 1.1~1.3 子条款）

  LLM 结构化:
    输入: 30个候选条款的文本
    输出:
      · 30 个一级条款 + 45 个二级子条款 = 75 个条款节点
      · 每个节点含 clause_type 标签
      · 识别到 8 个定义条款
      · 识别到 23 个交叉引用
      · 识别当事方: 甲方=XX科技, 乙方=YY制造

  后处理:
    · 编号连续性: 第一条~第三十条，无跳号 ✅
    · 层级嵌套: 所有子条款均在对应一级条款内 ✅
    · 字符偏移: 75个条款的 char_offset 全部对齐 ✅

  输出: ClauseGraph (75 nodes, 23 edges) + positioning_data
```

### Step 4: 快速过滤 (~5ms)

```
检查1: 禁用词匹配 (卡片②)
  租户禁用词表: 无命中
  全局敏感词表: 无命中

检查4: 文本基础核对 (卡片①)
  · 第12条第2款: 引号未配对 → minor
  · 第18条: "人民币伍佰万元(¥5,000,000元)" → 大小写金额一致 ✅
  · 第23条: "已知或应知" → 常见法律用语 ✅

输出: 卡片① 1个问题(minor), 卡片② 0个问题
```

### Step 5: ACE 上下文组装 (~600ms)

```
路径A: 按内容类型 (PG, ~50ms)
  content_type = "采购合同" → 命中 25 条法条

路径B: 按产品类型 (PG, ~30ms)
  product_type = null (通用合同) → 命中 15 条合同法通用法条

路径C: 按语义 (Milvus, ~300ms)
  对 75 个条款中的关键条款(定义/违约/争议/终止=20个)做向量检索
  命中 30 条法条 (去重后)

路径D: 案例检索 (Milvus, ~200ms)
  对关键条款做案例检索
  命中 8 条相似合同审查案例

路径E: 企业规则 (PG, ~20ms)
  tenant_id = 'xxx' → 3 条合同类自定义规则

合并去重 → 按 norm_type 分桶:
  禁止类: 12条, 义务类: 15条, 权利类: 8条, 定义类: 5条 = 40条法条
  案例: 8条
  规则: 3条
```

### Step 6: 逐条款审查 (~15s, 并行)

```
对 20 个关键条款并行执行 LLM 审查:
  · 每条款独立构建 prompt (条款文本 + 相关法条 + 案例)
  · 并发: 10 路并行 (Semaphore 控制)

审查结果汇总 (卡片④ 语义与合规审查):

  第5条: 质量标准
    → compliant (✅)

  第8条: 违约责任
    → violation (major): 违约金比例30%高于行业惯例
    → exact_substring: "违约金为合同金额的百分之三十"
    → suggestion_type: negotiation_point
    → suggestion: "建议协商降低至10-20%"

  第12条: 保密条款
    → needs_review (minor): 保密期限未明确
    → exact_substring: "在合同终止后的合理期限内"
    → suggestion_type: revision
    → suggestion: "在合同终止后两年内"

  第15条: 免责条款
    → violation (critical): 甲方免责范围过宽
    → exact_substring: "甲方不承担任何间接损失的赔偿责任"
    → suggestion_type: negotiation_point

  ... (其余条款)
```

### Step 7: 模板 Diff 分析 (~3s)

```
匹配到最佳模板: "标准采购合同模板 v2.1"
  合同类型匹配: purchase ✅
  向量相似度: 0.87

条款对齐结果:
  匹配: 26/30 条款
  缺失: 2 条 (交货验收条款、知识产权条款)
  新增: 1 条 (独家经销条款)
  偏离: 3 条 (违约金比例、保密期限、争议管辖)

→ 生成 6 张 Diff 卡片 (归入卡片③和⑤)
```

### Step 8: 跨条款一致性检查 (~5s)

```
跨条款一致性 Agent 执行 (卡片⑤):

  权责对称性:
    · 甲方有权在乙方违约时解除合同 (第10条)
    · 乙方无对等解除权 → asymmetry_issue (major)

  争议解决自洽性:
    · 第28条约定北京仲裁委员会仲裁 ✅
    · 无诉讼/仲裁矛盾 ✅
    · 仲裁机构名称完整 ✅

  终止条款完整性:
    · 合同期限: 明确 ✅
    · 提前终止条件: 列举 ✅
    · 终止后交接义务: 缺失 → missing_element (major)

  金额一致性:
    · 合同金额 500万元: 第3条、第4条、第8条
    · 第4条: 首付30%=150万 ← 500×30%=150 ✅
    · 第8条: 违约金30%=100万 ← 500×30%=150≠100 ❌ critical!

输出: 卡片⑤ 4个问题 (1 critical, 2 major, 1 info)
```

### Step 9: 修订建议生成 + 校验 (~3s)

```
对所有 suggestion_type=revision 的建议执行校验:

  第12条修订: "在合同终止后两年内" (替换 "合理期限内")
    · 最小改动: 编辑距离=6, 改动比例=15% ✅
    · 禁用词检查: 无命中 ✅
    · 跨条款影响: 第25条引用了第12条 → 无矛盾 ✅
    → validated_revision ✅

  第8条修订: 违约金计算结果 100万→150万
    · 改动: 仅修改金额数字 ✅
    · 跨条款影响: 第4条付款金额不受影响 ✅
    → validated_revision ✅
```

## 附：合同审查与 v1 营销审查的能力矩阵

| 能力 | v1 营销审查 | v2 合同审查 | 差异 |
|------|-----------|-----------|------|
| 内容解析 | OCR/文档解析→分段 | 文档解析→条款树解析 | 条款层级替代段落分段 |
| 检索路径 | 5路混合检索 | 5路+合同模板匹配 | 新增模板 Diff |
| LLM 审查 | 逐段审查 | 逐条款审查+跨条款一致性 | 增加一致性 Agent |
| 定位 | 段落级 (segment_index) | 字符级 (char_offset+length) | 精度提升两个数量级 |
| 修订建议 | 自由文本 suggestion | 三层分类 suggestion_type | 区分 tip/revision/negotiation |
| 知识底座 | 法条知识库 | 法条+合同模板库 | 新增模板库 |
| 审查卡片 | ①②③④ | ①②③④⑤ | 新增逻辑与条款卡片 |
| 图谱 | 法条间知识图谱 | 法条图谱+合同内部条款图谱 | 新增合同内部图谱 |
