## 1. 内容路由核心思路

### 1.1 语义驱动检索 — 核心原则不变

v2 延续 v1 的核心理念：

> **法条/规则检索不依赖预设的「文档类型 → 规则集」映射，内容的语义本身决定了检索到哪些法条。**

举例说明——现在扩展到合同场景：
- 合同里写了"甲方不承担任何责任" → 向量搜索命中《民法典》第 497 条（免除己方责任的格式条款无效）
- 营销海报里写了"收益率 20%" → 向量搜索命中第 24 条（不得以预期收益率宣传）
- 招募说明书缺少"风险揭示章节" → 向量搜索命中信息披露法条
- 服务合同缺少数据保护条款 → 向量搜索命中《个人信息保护法》相关条款

不管文档被分类为"销售合同"还是"营销海报"还是"招募说明书"，只要它的文字语义与某条法规/规则的违规模式相似，就会被检索到。

### 1.2 混合检索策略

系统采用三路混合检索策略，各有分工：

| 检索方式 | 引擎 | 匹配逻辑 | 核心优势 |
|----------|------|----------|----------|
| **语义向量检索** | Milvus | 对内容段落做 Embedding，与法条/规则的多粒度向量做相似度匹配 | 处理**含义层面**的匹配，能捕获语义变体 |
| **结构化字段查询** | PostgreSQL | 对 `document_type`、`product_type` 等字段做精确匹配 | 提供**确定性、保证命中**的结果 |
| **关键词全文检索** | Elasticsearch | 对法条原文、关键短语做全文搜索 | 捕获**精确术语匹配**——精准命中含有该术语的法条 |

三路检索结果合并去重后，共同构成 LLM 审查的法规上下文。

### 1.3 路由的实质

v2 的路由实质与 v1 保持一致，但扩展了输入维度：

```
内容路由的本质（v2 扩展）：

  传统方案:  文档 → 类型标签 → 预设规则集 → 审查
                      ↑ 人工维护，易遗漏

  v2 系统:   文档 → ┬── 文档类型注册表 → 选择解析器 + 必备元素清单
                    ├── 结构化字段查询 (类型/产品) ── 确定性命中
                    ├── 语义向量检索 (内容文本)     ── 模糊语义匹配
                    └── 关键词全文检索 (术语)       ── 精确词汇命中
                                 │
                                 ▼
                          合并去重 → 动态上下文 → LLM 审查（5 类审查卡片）
```

## 2. 文档类型注册表 (DocumentTypeRegistry)

### 2.1 设计动机

v1 系统仅支持营销物料，文档类型隐含在代码逻辑中。v2 面临的挑战是：

- 合同有 8+ 种子类型，营销物料有 5+ 种，金融文档有 3+ 种
- 每种文档类型有不同的解析方式、必备元素、适用审查卡片
- 企业可能需要自定义新的文档类型

因此引入 **DocumentTypeRegistry** — 一个可扩展的文档类型注册表，让新增文档类型成为"配置动作"而非"代码修改"。

### 2.2 注册表结构

```
┌────────────────────────────────────────────────────────────────────────────┐
│  DocumentTypeRegistry                                                       │
│                                                                            │

│                                                                            │

│  │  字段                    类型            说明                         │  │
│  │  ──────────────────────────────────────────────────────────────────  │  │
│  │  type_id                 String          唯一标识 (如 "sales_contract") │ │
│  │  display_name            String          显示名称 (如 "销售合同")      │  │
│  │  category                Enum            大类: CONTRACT / MARKETING   │  │

│  │  parser_id               String          关联的解析器ID               │  │
│  │  checklist               List<Element>   必备元素清单                 │  │
│  │  required_elements       List<String>    法定必备条款/元素            │  │

│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                            │
│  审查卡片类别 (CardType) — 5 类:                                            │
│                                                                            │
│  ┌─────────────────────────────────────────────────────────────────┐      │
│  │  1. COMPLIANCE      — 合规性审查 (法律法规符合性)                 │      │

└────────────────────────────────────────────────────────────────────────────┘

│                    │ 统一内容表示        │                             │
│                    │ UnifiedContent     │                             │
│                    │                    │                             │
│                    │ • segments: List   │  ← 分段的纯文本列表         │
│                    │ • metadata: Map    │  ← 文件元信息               │
│                    │ • layout_info: Opt │  ← 布局信息（图片专用）     │
│                    │ • completeness: Opt│  ← 完整性检查结果           │
│                    │ • clauses: Opt     │  ← 条款层级（合同专用）     │
│                    │ • definitions: Opt │  ← 定义条款提取（合同专用） │
│                    └────────────────────┘                             │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.2 ContractParser — 合同解析器

合同解析器是 v2 新增的核心解析器，专门处理合同文档的结构化解析。它不是简单的文本分段，而是进行**条款层级识别**和**定义抽取**。

```
┌──────────────────────────────────────────────────────────────────────┐
│  ContractParser — 合同解析器                                          │
│                                                                      │
│  输入: 合同文档 (PDF / Word / 纯文本)                                 │
│                                                                      │
│  Step 1: 基础文本提取                                                │
│    PDF → Apache PDFBox 提取文字                                      │
│    Word → Apache POI 提取文字 + 样式信息                              │
│    纯文本 → 直接读取                                                 │
│                                                                      │
│  Step 2: 条款层级识别 (ClauseHierarchyRecognizer)                    │
│    ┌────────────────────────────────────────────────────────────┐    │
│    │  识别合同的层级结构:                                         │    │
│    │                                                            │    │
│    │  正则 + 规则引擎识别:                                        │    │
│    │    · "第X条" / "第X章" → Level 1 (条/章)                    │    │
│    │    · "X.Y" / "(一)" / "第X款" → Level 2 (款)               │    │
│    │    · "X.Y.Z" / "1)" / "第X项" → Level 3 (项)              │    │
│    │    · 未编号段落 → 归属到最近的上级条款                       │    │
│    │                                                            │    │
│    │  输出: 树形条款结构                                         │    │
│    │                                                            │    │
│    │  第一条 合同主体                                             │    │
│    │    ├── 1.1 甲方: XX公司                                     │    │
│    │    └── 1.2 乙方: YY公司                                     │    │
│    │  第二条 标的物与价款                                         │    │
│    │    ├── 2.1 标的物描述                                       │    │
│    │    ├── 2.2 合同总价款                                       │    │
│    │    └── 2.3 支付方式                                         │    │
│    │      ├── 2.3.1 首付款                                       │    │
│    │      └── 2.3.2 尾款                                         │    │
│    │  第三条 违约责任                                              │    │
│    │    ├── 3.1 甲方违约                                         │    │
│    │    └── 3.2 乙方违约                                         │    │
│    │  ...                                                        │    │
│    └────────────────────────────────────────────────────────────┘    │
│                                                                      │
│  Step 3: 定义条款提取 (DefinitionExtractor)                          │
│    ┌────────────────────────────────────────────────────────────┐    │
│    │  识别合同中的定义条款:                                       │    │
│    │                                                            │    │
│    │  模式匹配:                                                  │    │
│    │    · "本合同所称'XXX'是指..." → 提取 XXX 的定义              │    │
│    │    · "'XXX'指..." → 提取定义                                │    │
│    │    · 定义章节(通常是第一条)中的所有术语                       │    │
│    │                                                            │    │
│    │  输出: 定义字典                                             │    │
│    │    {                                                        │    │
│    │      "关联方": "与甲方存在控制或重大影响关系的法人或自然人",   │    │
│    │      "交付日": "合同签署后30个工作日",                        │    │
│    │      "不可抗力": "地震、洪水、战争..."                        │    │
│    │    }                                                        │    │
│    │                                                            │    │
│    │  定义字典在后续审查中的作用:                                  │    │
│    │    · 放入 LLM prompt，帮助理解合同用语                       │    │
│    │    · 检查定义是否在正文中被正确使用                           │    │
│    │    · 检查是否存在未定义但使用的术语                           │    │
│    └────────────────────────────────────────────────────────────┘    │
│                                                                      │
│  Step 4: 条款交叉引用识别                                            │
│    ┌────────────────────────────────────────────────────────────┐    │
│    │  识别条款间的引用关系:                                       │    │
│    │                                                            │    │
│    │  "依照本合同第8.3条规定" → 建立 当前条款 → 8.3 的引用边     │    │
│    │  "按第五条约定的价款" → 建立 当前条款 → 第五条 的引用边     │    │
│    │                                                            │    │
│    │  输出: 条款引用图 (adjacency list)                           │    │
│    │    3.1 → [2.2, 5.1]  (第3.1条引用了第2.2条和第5.1条)       │    │
│    │    7.2 → [3.1, 3.2]  (第7.2条引用了第3.1和3.2条)           │    │
│    └────────────────────────────────────────────────────────────┘    │
│                                                                      │
│  Step 5: 组装 UnifiedContent                                        │
│    · segments: 每个条款作为一个 segment                              │
│    · clauses: 树形条款结构 (合同专属)                                │
│    · definitions: 定义字典 (合同专属)                                │
│    · clause_references: 条款引用图 (合同专属)                        │
│    · metadata: 合同类型、当事方信息、签署日期等                      │
└──────────────────────────────────────────────────────────────────────┘
```

## 4. 完整性检查器 (CompletenessChecker)

### 4.1 通用化设计

v2 的 `CompletenessChecker` 不再硬编码各文档类型的必备元素，而是**从 DocumentTypeRegistry 动态加载**。

```
┌──────────────────────────────────────────────────────────────────────┐
│  CompletenessChecker v2 — 通用完整性检查                               │
│                                                                      │
│  输入: UnifiedContent + DocumentTypeDefinition                       │
│                                                                      │
│  处理逻辑:                                                           │
│                                                                      │
│  1. 从 DocumentTypeDefinition 加载 required_elements                 │
│     → 不再硬编码，来源于注册表                                        │
│                                                                      │
│  2. 从知识库加载动态必备元素                                           │
│     SELECT * FROM law_knowledge                                      │
│     WHERE norm_type = '必备'                                         │
│     AND document_type IN applicable_document_types                   │
│     AND status = 'published'                                         │
│     → 法律法规更新后自动反映到完整性检查                               │
│                                                                      │
│  3. 合并: 注册表必备元素 ∪ 知识库动态必备元素 = 完整检查清单          │
│                                                                      │
│  4. 对每个必备元素执行检查:                                           │
│                                                                      │
│     if 文档类型 ∈ CONTRACT:                                          │
│       → 在 clauses 树形结构中查找匹配条款                             │
│       → 支持语义匹配 (阈值 > 0.80)                                   │
│       例: required="违约责任条款"                                     │
│           在 clauses 中找到 "第七条 违约责任" → 匹配 ✅               │
│                                                                      │
│     if 文档类型 ∈ MARKETING:                                         │
│       → 在 segments 中搜索关键词或语义匹配                            │
│       例: required="风险提示语"                                       │
│           在 segments 中找到 "基金有风险，投资需谨慎" → 匹配 ✅       │
│                                                                      │
│     if 文档类型 ∈ FINANCIAL_DOC:                                     │
│       → 在文档目录/章节标题中查找                                     │
│       例: required="风险揭示章节"                                     │
│           在目录中找到 "第四章 风险揭示" → 匹配 ✅                    │
│                                                                      │
│  输出: missing_elements 列表, 每条包含:                               │
│    · element: 缺失的元素名称                                         │
│    · requirement: 法定/企业要求描述                                   │
│    · source: "registry" | "law_knowledge" | "custom_rule"            │
│    · severity: "critical" | "recommended"                            │
│    · suggestion: 补充建议                                            │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2 必备元素来源

必备元素由三个来源合并：

| 来源 | 优先级 | 说明 | 更新方式 |
|------|--------|------|----------|
| **DocumentTypeRegistry** | 最高 | 文档类型注册表中定义的结构化必备元素 | 管理员编辑注册表 |
| **知识库法条** | 高 | 从 law_knowledge 中自动提取的法定必备要素 | 新法规发布 → LLM 解析 → 人工确认 |
| **企业自定义规则** | 中 | 企业通过自定义规则定义的额外必备项 | 租户管理员自行配置 |

当三个来源的必备元素发生冲突时，取并集——即所有来源要求的元素都需要检查。

## 5. 法条引用校验器 (CitationVerifier) — 增强版

### 5.1 三步校验流程

v2 保持 v1 的三步校验核心逻辑，同时增强了模糊匹配和幻觉标记的能力。

```
LLM 返回的每条法条引用
          │
          ▼
┌──────────────────────────────────────────────────────────────┐
│  CitationVerifier v2                                          │
│                                                               │
│  Step 1: 精确匹配                                             │
│    查询知识库:                                                 │
│    SELECT * FROM law_articles                                 │
│    WHERE article_id = :llm_cited_article_id                   │
│    AND law_name LIKE :llm_cited_law_name                      │
│                                                               │
│    如果命中 → 校验通过 ✅ (verified)                           │
│    如果未命中 → 进入 Step 2                                   │
│                                                               │
│  Step 2: 模糊匹配 (v2 增强)                                   │
│    2a. 法律名称模糊匹配:                                       │
│      · 全称/简称映射表 (如 "基金法" ↔ "证券投资基金法")         │
│      · 编辑距离 < 3 的名称匹配                                 │
│      · 别名库匹配 (如 "公司法" ↔ "中华人民共和国公司法")        │
│                                                               │
│    2b. 条款编号模糊匹配:                                       │
│      · 层级放宽: "第24条第3款" → 查 "第24条*"                  │
│      · 款项遗漏: "第24条" → 查 "第24条*" 所有款项              │
│      · 阿拉伯/中文混用: "第24条" ↔ "第二十四条"                │
│                                                               │
│    2c. 语义匹配 (v2 新增):                                     │
│      · 对 LLM 引用的法条文本做 Embedding                       │
│      · 在 Milvus 中搜索 top-3 最相似的真实法条                 │
│      · 相似度 > 0.90 → 视为匹配                               │
│                                                               │
│    如果找到匹配 → 替换引用并标记 "引用已修正" ⚠️ (corrected)   │
│    如果仍无匹配 → 进入 Step 3                                  │
│                                                               │
│  Step 3: 幻觉标记                                             │
│    该引用标记为 "无法验证的引用" ❌ (unverified)               │
│    处理策略:                                                   │
│    · 保留 LLM 的审查判断和理由 — 判断本身可能正确              │
│    · 法条引用标记为 "未经验证，需人工确认"                      │
│    · 在审查卡片中醒目提示 ⚠️ 标记                             │
│    · 自动提升该条目的人工复核优先级至 P0                       │
│    · 记录幻觉日志: 方便后续分析 LLM 幻觉模式                  │
│                                                               │
│  输出: 校验后的法条引用列表，每条附状态:                        │
│    verified / corrected / unverified                          │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 模糊匹配增强

v2 的模糊匹配增加了三项能力：

```
┌──────────────────────────────────────────────────────────────────┐
│  模糊匹配增强 (v2 新增)                                            │
│                                                                  │
│  能力1: 法律名称别名库                                            │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │  别名库存储在 PostgreSQL 的 law_name_aliases 表:            │ │
│  │                                                            │ │
│  │  canonical_name                  aliases                   │ │
│  │  ─────────────────────────────────────────────────────── │ │
│  │  中华人民共和国民法典             民法典, 民法总则          │ │
│  │  证券投资基金法                   基金法                   │ │
│  │  公开募集证券投资基金销售         基金销售管理办法,         │ │
│  │  机构监督管理办法                 基金销售办法              │ │
│  │  中华人民共和国劳动合同法         劳动合同法, 劳动法       │ │
│  └────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  能力2: 编辑距离兜底                                              │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │  当别名库未命中时，使用 Levenshtein 编辑距离:               │ │
│  │  if editDistance(llm_law_name, db_law_name) <= 3:          │ │
│  │    → 视为匹配候选，人工确认后加入别名库                     │ │
│  └────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  能力3: 语义向量兜底                                              │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │  当法律名称和条款编号都无法匹配时:                          │ │
│  │  1. 取 LLM 输出的 law_reference.original_text              │ │
│  │  2. Embedding → Milvus 检索 top-3                         │ │
│  │  3. 如果最高相似度 > 0.90:                                 │ │
│  │     → 用该法条替换引用                                     │ │
│  │     → 标记为 corrected (语义修正)                          │ │
│  │  4. 否则 → unverified                                     │ │
│  └────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

### 5.3 幻觉标记与降级策略

```
幻觉标记的降级策略:

  场景: LLM 引用了 "《合同法》第114条" — 但《合同法》已被《民法典》吸收

  Step 2 模糊匹配:
    · 法律名称别名库: "合同法" → "中华人民共和国民法典 · 合同编"
    · 条款编号映射: 原《合同法》第114条 → 《民法典》第585条
    · 匹配成功 → corrected
    · 引用修正为: 《民法典》第585条 (原《合同法》第114条)

  场景: LLM 引用了完全不存在的法条

  Step 3 幻觉标记:
    · 该条审查结论保留（LLM 的判断可能正确）
    · 法条引用标记为 unverified
    · 人工复核优先级提升至 P0
    · 幻觉日志记录:
      {
        "llm_cited": "《企业信息安全管理条例》第32条",
        "search_attempts": ["精确匹配:未命中", "别名库:未命中",
                           "编辑距离:未命中", "语义检索:最高0.72<0.90"],
        "verdict": "unverified",
        "timestamp": "2026-04-20T10:30:00Z"
      }
```

### 5.4 校验结果对后续流程的影响

| 校验状态 | 标记 | 对风险评分的影响 | 对人工复核的影响 |
|----------|------|-----------------|-----------------|
| `verified` ✅ | 引用已验证 | 得分权重 × 1.0（全额计算） | 正常优先级 |
| `corrected` ⚠️ | 引用已修正 | 得分权重 × 0.8（略降） | 优先级适度提升 |
| `unverified` ❌ | 未经验证 | 得分权重 × 0.5（大幅降低） | 优先级提升至 P0（最高） |

## 6. 风险评分与引用权重

### 6.1 Issue 级评分

每个被发现的问题有一个严重程度，对应固定分值。v2 沿用 v1 体系：

| 严重程度 | 含义 | 分值 | 合同场景示例 | 营销场景示例 |
|----------|------|------|-------------|-------------|
| `critical` | 严重违规/风险 | **+30** | 免除己方全部责任的格式条款 | 保本承诺、虚假陈述 |
| `major` | 重要违规/风险 | **+20** | 违约金比例过高(超合同额200%) | 业绩数据缺失截止日期 |
| `minor` | 轻微违规/风险 | **+10** | 表述不够严谨的条款 | 措辞不当、诱导性表述 |
| `info` | 建议优化 | **+5** | 可优化的合同条款表述 | 可优化的表述 |

缺失必备元素也产生分值：

| 缺失类型 | 分值 | 示例 |
|----------|------|------|
| 缺失 `critical` 级必备元素 | **+25** | 合同缺少违约责任条款 / 海报缺少风险提示 |
| 缺失 `recommended` 级必备元素 | **+10** | 合同缺少不可抗力条款 / 缺少免责声明 |

### 6.2 引用校验加权因子

| 引用校验状态 | 加权因子 | 说明 |
|-------------|---------|------|
| `verified` | × 1.0 | 法条引用已验证，分值全额计算 |
| `corrected` | × 0.8 | 法条引用经修正，分值略降 |
| `unverified` | × 0.5 | 法条引用未验证，分值大幅降低 |

### 6.3 Task 级评分

```
overall_risk_score = Σ (issue_severity_score × citation_weight)
                   + Σ (missing_element_score)

封顶: 100 分
```

风险等级映射：

| 总分范围 | 风险等级 | 标识 | 含义 |
|----------|---------|------|------|
| 0 – 20 | `low`（低风险） | 🟢 绿色 | 可直接通过（抽样复核） |
| 21 – 50 | `medium`（中风险） | 🟡 黄色 | 建议人工复核 |
| 51 – 100 | `high`（高风险） | 🔴 红色 | 必须人工复核 |

### 6.4 完整计算示例

**合同审查场景**：审查一份服务合同，发现以下问题：

| # | 问题 | severity | 基础分 | 引用状态 | 加权因子 | 加权后分值 |
|---|------|----------|--------|---------|---------|-----------|
| 1 | 甲方免责条款过于宽泛 | critical | 30 | verified | × 1.0 | **30** |
| 2 | 缺少数据保护条款 | — | — | — | — | +25 (缺失critical必备) |
| 3 | 违约金比例未约定上限 | major | 20 | corrected | × 0.8 | **16** |
| 4 | 争议解决条款表述模糊 | minor | 10 | verified | × 1.0 | **10** |

```
overall_risk_score = 30 + 16 + 10 + 25 = 81
risk_level = high (81 > 50)
```

**营销审查场景**：审查一张基金海报，发现以下问题：

| # | 问题 | severity | 基础分 | 引用状态 | 加权因子 | 加权后分值 |
|---|------|----------|--------|---------|---------|-----------|
| 1 | 暗示保本 | critical | 30 | verified | × 1.0 | **30** |
| 2 | 业绩数据缺少截止日期 | major | 20 | verified | × 1.0 | **20** |
| 3 | 诱导性推荐 | minor | 10 | corrected | × 0.8 | **8** |
| — | 缺失风险提示声明 | — | — | — | — | +25 (缺失critical必备) |

```
overall_risk_score = 30 + 20 + 8 + 25 = 83
risk_level = high (83 > 50)
```

## 7. 建议类型分类 (SuggestionType)

### 7.1 三种建议类型

v2 引入 `suggestion_type` 字段，将审查建议分为三种类型，解决 v1 中所有建议混为一谈的问题。这在合同场景尤为关键——合同修订建议需要区分"纯提示"和"可直接采纳的修订文本"。

```
┌──────────────────────────────────────────────────────────────────────┐
│  SuggestionType — 三种建议类型                                        │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  1. TIP (提示)                                                 │ │
│  │                                                                │ │
│  │  定义: 告知性提示，无需直接修改文档                              │ │
│  │  适用: 风险告知、注意事项、合规提醒                              │ │
│  │  示例:                                                         │ │
│  │    · "该条款的违约金比例(合同额300%)可能被法院调低"              │ │
│  │    · "此表述在部分地区可能存在合规风险"                          │ │
│  │    · "建议关注该条款与第5.2条的潜在冲突"                        │ │
│  │  操作: 阅读即可，无需修改文档                                   │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  2. REVISION (修订建议)                                        │ │
│  │                                                                │ │
│  │  定义: 提供可直接采纳的替换文本                                  │ │
│  │  适用: 明确的文本修改、条款替换、内容补充                        │ │
│  │  示例:                                                         │ │
│  │    · 原文: "甲方不承担任何责任"                                 │ │
│  │      修订: "甲方就其过错行为承担与过错程度相适应的赔偿责任，     │ │
│  │            但不超过本合同总金额的100%"                           │ │
│  │    · 原文: "收益率20%"                                         │ │
│  │      修订: "截至2026年3月31日，近一年收益率为20.3%               │ │
│  │            （数据来源：XX），过往业绩不代表未来表现"              │ │
│  │  操作: 用户可直接采纳修订文本替换原文                            │ │
│  │  约束: 修订文本必须是最小化改动，保留原意                        │ │
│  └────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  3. NEGOTIATION_POINT (协商要点)                                │ │
│  │                                                                │ │
│  │  定义: 指出需要与对方协商的要点，无法单方修改                    │ │
│  │  适用: 合同谈判中的权责分配、商业条款调整                        │ │
│  │  示例:                                                         │ │
│  │    · "违约金条款仅约束乙方，建议协商增加甲方对等违约责任"        │ │
│  │    · "知识产权归属约定为甲方所有，如涉及乙方既有IP，             │ │
│  │       建议协商明确既有IP的排除条款"                              │ │
│  │    · "竞业限制期限3年可能超过法定上限，建议协商调整为2年"        │ │
│  │  操作: 需要与合同对方协商后决定                                  │ │
│  │  输出: 提供协商要点 + 建议方向 + 参考案例/法条                  │ │
│  └────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

### 7.2 建议类型的约束规则

```
建议类型的生成约束:

┌────────────────────────────────────────────────────────────────────┐
│                                                                    │
│  规则1: REVISION 类型必须提供完整的替换文本                         │
│    · 替换文本必须语法完整、可直接粘贴使用                           │
│    · 替换文本不得引入新的合规风险                                   │
│    · 替换文本应尽量保留原文的商业意图                               │
│                                                                    │
│  规则2: REVISION 类型的 diff 校验                                  │
│    · 系统自动计算原文与修订文本的 diff                              │
│    · 如果 diff 变更率 > 70%，降级为 NEGOTIATION_POINT              │
│      (变更过大说明不是简单修订，需要协商)                           │
│                                                                    │
│  规则3: NEGOTIATION_POINT 必须提供协商方向                          │
│    · 不能只说"建议协商"，必须给出具体的协商建议                    │
│    · 必须说明为什么需要协商（法律依据或商业考量）                   │
│                                                                    │
│  规则4: TIP 类型不提供替换文本                                     │
│    · 只提供说明性信息                                              │
│    · 如果 LLM 在 TIP 中给出了修改建议，后处理自动升级为 REVISION   │
│                                                                    │
│  规则5: 分类歧义时的处理                                           │
│    · LLM 不确定分类 → 默认为 TIP (最保守)                         │
│    · 后处理阶段可根据规则2自动调整分类                              │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

### 7.3 各文档类型的建议类型分布

不同文档类型的审查结果中，三种建议类型的预期分布不同：

| 文档类型 | TIP 占比 | REVISION 占比 | NEGOTIATION_POINT 占比 |
|----------|---------|--------------|----------------------|
| **销售/采购合同** | 20% | 30% | 50% |
| **服务合同** | 15% | 35% | 50% |
| **劳动合同** | 25% | 45% | 30% |
| **保密协议** | 30% | 50% | 20% |
| **营销海报** | 30% | 65% | 5% |
| **微信推文** | 35% | 60% | 5% |
| **招募说明书** | 40% | 50% | 10% |

合同类型的 NEGOTIATION_POINT 占比高，因为合同本质上是双方协商的产物，很多条款无法单方面修改。营销物料的 REVISION 占比高，因为大部分问题可以由发布方单方面修改。
