## 一、回应 Gemini 的 5 个关键质疑

### R1: 延迟预算过于乐观 → 拆分 p50/p95

**Gemini 原始质疑：**
> "5 路检索 200-500ms" 的延迟预算过于乐观。Milvus 向量检索 + Embedding 模型推理单次就要 30-80ms，长文档分 10 段需要 10 次检索，Neo4j Cypher 在复杂路径场景会达到 100-300ms。真实 p95 应按 600-1500ms 规划。

**v2 回应：完全采纳，延迟预算重新拆分为 p50/p95 两档。**

```
v1 延迟预算（乐观版本）:
  五路检索: < 500ms          ← 不区分 p50/p95
  短内容审查: < 10s           ← 不考虑模型冷启动

v2 延迟预算（务实版本）:
  五路检索:
    p50 < 400ms              ← 典型场景，4段文本，3路并行
    p95 < 1000ms             ← 长文档10段 + 图谱查询(Phase 3+)

  单次审查:
    短内容(<1000字):  p50 < 8s,  p95 < 15s
    中等内容:         p50 < 15s, p95 < 25s
    长文档/合同:      p50 < 30s, p95 < 60s

  具体拆分:
  ┌────────────────────────┬───────────┬───────────┐
  │ 阶段                    │ p50       │ p95       │
  ├────────────────────────┼───────────┼───────────┤
  │ 内容解析(OCR/文档)      │ 500ms     │ 3s        │
  │ Embedding 生成(4段)     │ 120ms     │ 300ms     │
  │ Milvus 向量检索(并行)   │ 150ms     │ 400ms     │
  │ PG 结构化查询(并行)     │ 30ms      │ 80ms      │
  │ ES 关键词检索(并行)     │ 50ms      │ 150ms     │
  │ Neo4j 图谱(Phase 3+)   │ 100ms     │ 300ms     │
  │ 上下文组装              │ 30ms      │ 50ms      │
  │ LLM 推理(主链路)        │ 5s        │ 12s       │
  │ 后处理(法条校验)        │ 50ms      │ 100ms     │
  └────────────────────────┴───────────┴───────────┘

  关键假设:
  · LLM: Gemini 2.5 Pro, 15K input tokens, streaming
  · Embedding: bge-large-zh-v1.5, 本地 GPU 推理
  · Milvus: IVF_SQ8 索引, 3副本, 预热状态
  · Phase 1-2 不含 Neo4j, p95 检索可控在 600ms 以内
```

### R2: LLM 成本失控 → Prompt 缓存 + 模型路由

**Gemini 原始质疑：**
> 每次审查 15-20K tokens 的上下文，GPT-4o 单次成本约 $0.067，按 100 QPS 年化约 200 万美金。设计中完全没有提 Prompt Caching、小模型路由、法条上下文 KV 缓存。

**v2 回应：完全采纳，新增 Prompt 缓存层和模型路由层。**

```
┌─────────────────────────────────────────────────────────────────┐
│  成本控制三板斧                                                   │
│                                                                  │
│  ① Prompt 缓存层                                                │
│                                                                  │
│  原理: 审查 prompt 中 ~80% 是法条上下文，对于同类型内容，          │
│  法条上下文高度重复（同一天审查100张公募基金海报，法条部分          │
│  几乎完全相同）。                                                 │
│                                                                  │
│  实现:                                                           │
│  · 对 prompt 的法条上下文部分计算语义指纹(SHA-256)                │
│  · 指纹相同 → 复用 LLM API 原生 prompt cache                    │
│    (Anthropic: cached_content, OpenAI: predicted outputs)        │
│  · 指纹相似(编辑距离<5%) → 复用相同的法条上下文排列顺序           │
│    以最大化 LLM 侧 KV cache 命中率                               │
│  · Redis 存储: key=指纹, value=法条上下文文本, TTL=24h           │
│                                                                  │
│  预期效果:                                                       │
│  · 同类型内容的 prompt cache 命中率 > 70%                        │
│  · 命中时 input token 成本降低 50-90%（取决于 LLM 厂商策略）     │
│  · 命中时首字节延迟降低 30-50%                                   │
│                                                                  │
│  ② 模型路由层 (ModelRouter)                                      │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  ModelRouter 路由规则                                      │   │
│  │                                                          │   │
│  │  输入: document_type, content_length, estimated_tokens,   │   │
│  │        risk_hint (快速过滤阶段的初步风险信号)              │   │
│  │                                                          │   │
│  │  路由策略:                                                │   │
│  │  · 短文本(<500字) + 无禁用词命中 → 4o-mini / Gemini Flash │   │
│  │    成本: ~$0.005/次, 延迟: 2-4s                          │   │
│  │  · 中等文本 + 营销材料 → Gemini 2.5 Pro / GPT-4o         │   │
│  │    成本: ~$0.03/次, 延迟: 5-10s                          │   │
│  │  · 长文档/合同 + 高复杂度 → Claude Sonnet / Gemini Pro    │   │
│  │    成本: ~$0.08/次, 延迟: 10-20s                         │   │
│  │  · 任何内容 + 法条引用unverified → 用更强模型重审          │   │
│  │                                                          │   │
│  │  降级策略:                                                │   │
│  │  · 主模型超时/失败 → 自动切换备用模型                     │   │
│  │  · 连续 3 次 JSON 解析失败 → 升级到更强模型               │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  ③ Token 预算精细化                                              │
│                                                                  │
│  · 法条摘要压缩: 每条法条从 ~150 tokens 压缩到 ~40 tokens       │
│  · 案例压缩: 每条案例从 ~80 tokens 压缩到 ~30 tokens            │
│  · 动态 max_tokens: 根据内容长度动态计算，避免预留过大输出空间   │
│                                                                  │
│  综合成本估算:                                                   │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  场景           v1成本/次    v2成本/次    降低比例        │   │
│  │  ─────────────────────────────────────────────────────── │   │
│  │  短文本(4o-mini) —          $0.005       新增(低成本路由) │   │
│  │  营销材料        $0.067     $0.020       -70%            │   │
│  │  合同审查        —          $0.060       新增             │   │
│  │  年化(100QPS)   $200万     $50-80万     -60~75%          │   │
│  └──────────────────────────────────────────────────────────┘   │

```

### R3: "越用越准"闭环存在退化风险 → 案例生命周期管理

**Gemini 原始质疑：**
> 人工复核员偏向简单 Confirm，案例库会被冗余 confirmed 案例污染。同一类违规在不同复核员之间尺度不一致，案例会互相打架。缺少案例淘汰机制。

**v2 回应：完全采纳，新增案例生命周期管理（增强 6）。**

详见第二节增强 6。核心设计：

1. **时间衰减权重**：案例创建超过 24 个月，检索权重逐步衰减至 0.7
2. **邻域采样防 bloat**：同一 embedding 邻域（cosine > 0.92）内，只保留 learning_value_score 最高的 top-5 条案例，其余归档
3. **定期一致性审计**：每月检测同一 original_text 存在矛盾 verdict 的案例对，推送合规团队裁定
4. **3 年归档策略**：创建超过 3 年且近 6 个月无检索命中的案例，自动标记为 archived，不参与检索但保留备查

### R4: Token 裁剪粒度太粗 → 按 norm_type 分桶

**Gemini 原始质疑：**
> 全局按 RRF 分数 top-K 裁剪法条，会导致某一违规类别的法条被集中保留，而另一类别被全部裁掉。例如"预期收益承诺"法条 RRF 分很集中，"信息披露不完整"法条分散，裁剪后后者可能全部丢失。

**v2 回应：完全采纳，改为按 norm_type 分桶后再裁剪。**

```
v1 裁剪策略 (有缺陷):
  所有法条合并 → 按 RRF 全局排序 → 取 top-40
  问题: "信息披露"类法条可能全部被排到 40 名之后

v2 裁剪策略 (分桶):
  ┌────────────────────────────────────────────────────────────┐
  │  Token 预算分桶裁剪                                         │
  │                                                            │
  │  Step 1: 按 norm_type 分桶                                 │
  │    禁止类法条:  [法条A, 法条B, 法条C, ...]  → 按RRF排序    │
  │    义务类法条:  [法条D, 法条E, ...]          → 按RRF排序    │
  │    权利类法条:  [法条F, ...]                 → 按RRF排序    │
  │    定义类法条:  [法条G, ...]                 → 按RRF排序    │
  │    程序类法条:  [法条H, ...]                 → 按RRF排序    │
  │                                                            │
  │  Step 2: 每桶保留 top-N                                    │
  │    禁止类: top-12 (禁止类通常是审查重点)                    │
  │    义务类: top-10 (必备元素/声明相关)                       │
  │    权利类: top-5  (权利类通常参考性较强)                    │
  │    定义类: top-5  (定义类辅助理解)                          │
  │    程序类: top-3  (程序类通常不直接产生违规)                │
  │    合计: ~35 条法条                                        │
  │                                                            │
  │  Step 3: 如果总 token 仍超预算                             │
  │    从每桶的尾部等比例裁剪，而不是全局裁剪                   │
  │                                                            │
  │  效果: 确保每种规范类型至少有代表法条进入上下文              │
  └────────────────────────────────────────────────────────────┘
```

## 二、采纳的 7 项增强方案

### 增强 1: 合规自检清单 (Compliance Checklist)

**来源：v1 增强，v2 沿用并扩展至合同场景。**

v1 的设计完全保留（按 `<内容类型, 产品类型>` 组合预定义检查项），v2 新增 `contract_type` 维度：

```
示例: <合同, 采购合同> 的合规自检清单:
┌───────────────────────────────────────────────────────────────┐
│ 检查项                              法条依据       检查方式    │
│ ──────────────────────────────────────────────────────────── │
│ 包含合同双方完整名称及统一社会信用代码  合同法         关键词     │
│ 包含合同标的物明确描述                 合同法第12条   语义匹配   │
│ 包含价款及支付方式条款                 合同法第12条   语义匹配   │
│ 包含违约责任条款                       合同法第12条   条款类型   │
│ 包含争议解决条款                       合同法         条款类型   │
│ 签署日期和生效条件                     合同法         关键词     │
└───────────────────────────────────────────────────────────────┘
```

存储位置：`compliance_checklist` 表，详见 07-infrastructure.md 3.2.13。

### 增强 2: 法条锚点验证（LLM 只输出 ID，系统回填原文）

**来源：v1 增强，v2 沿用，无变更。**

核心设计不变：
- LLM 只输出 `article_id` + `law_name`，不输出 `original_text`
- 后处理用 ID 查知识库，取出人工确认过的原文，强制回填
- 未查到的 ID → 标记 `unverified` → 提升人工复核优先级
- Prompt 指令："引用法条只需输出编号和法律名称，不需要输出法条原文"

**效果：法条内容被幻觉的概率降至 0%（所有展示的法条原文 100% 来自知识库）。**

### 增强 3: 多 Agent 编排（从 3-agent 升级为 StateGraph）

**来源：v1 "三智能体协作"概念，v2 升级为显式 StateGraph。**

v1 只定义了三个 Agent 名字（分段专家 + 摘要专家 + 终审专家），v2 做了以下实质升级：

| 维度 | v1 | v2 |
|------|----|----|
| 编排方式 | 概念性描述 | 显式 StateGraph DAG |
| 消息协议 | 未定义 | ReviewState 结构体，字段明确 |
| 条件分支 | 无 | document_type 决定走营销/合同流 |
| 并行策略 | "可以并行" | CompletableFuture + Semaphore 并发控制 |
| 合同流 | 无 | 条款解析→逐条审查→一致性检查→模板Diff→修订生成 |
| 状态持久化 | 无 | Redis，支持长文档断点续审 |
| 节点数 | 3 | 营销流 6 节点，合同流 10 节点 |

详见第一节 R5 的完整 StateGraph 图。

### 增强 4: 法条效力层级与重排 (Authority Level Reranking)

**来源：v1 增强，v2 沿用，无变更。**

`law_article` 表已包含 `authority_level` 字段（1-6），检索结果的重排公式：

```
最终排序分 = RRF_score × authority_weight × freshness_weight × validity_weight

authority_weight:    法律(1)=×1.5, 行政法规(2)=×1.3, 部门规章(3)=×1.2,
                    规范性文件(4)=×1.0, 自律规则(5)=×0.9, 监管问答(6)=×0.8
freshness_weight:   近1年=×1.2, 1-3年=×1.0, 3年以上=×0.9
validity_weight:    现行有效=×1.0, 已修改(有替代)=×0.3, 已废止=×0.0
```

### 增强 5: 黄金测试集与漂移监控（前移至 Phase 0）

### 增强 6: 案例生命周期管理 [v2 新增]

**来源：Gemini R3 建议，v2 新增。**

**问题本质：** 案例库无限增长会导致三个问题——(1) 检索结果被冗余 confirmed 案例挤占，高价值纠错案例被淹没；(2) 不同复核员的尺度差异使案例互相矛盾；(3) 过期法条关联的案例仍在参与检索。

```
┌─────────────────────────────────────────────────────────────────┐
│  案例生命周期管理                                                  │
│                                                                  │
│  ① 时间衰减                                                     │
│                                                                  │
│  案例在检索时的时效性权重:                                        │
│    创建于近 6 个月:     × 1.1                                    │
│    创建于 6-12 个月:    × 1.0                                    │
│    创建于 12-24 个月:   × 0.95                                   │
│    创建于 24-36 个月:   × 0.85                                   │
│    创建于 36 个月以上:  × 0.70                                   │
│                                                                  │
│  ② 邻域采样 (防止 embedding 空间 bloat)                          │
│                                                                  │
│  定期任务 (每月执行):                                             │
│  1. 对案例库做聚类 (DBSCAN, eps=0.08 in cosine space)           │
│  2. 每个聚类内:                                                  │
│     · 按 learning_value_score 降序排列                           │
│     · 保留 top-5 条活跃案例                                     │
│     · 其余标记为 sampled_out                                     │
│     · sampled_out 的案例不参与检索，但保留在数据库                │
│  3. 确保每个聚类内违规/合规两种 verdict 各至少保留 1 条           │
│                                                                  │
│  ③ 归档策略                                                      │
│                                                                  │
│  自动归档条件 (满足全部):                                         │
│  · 创建时间 > 3 年                                               │
│  · 近 6 个月内被检索命中次数 = 0                                 │
│  · 非 is_typical 标记                                            │
│  · 关联法条仍为 is_current = true                                │
│                                                                  │
│  归档行为:                                                       │
│  · status → archived                                             │
│  · Milvus 中的向量标记为 inactive (不参与检索)                    │
│  · PostgreSQL 数据保留 (可手动恢复)                               │
│                                                                  │
│  ④ 一致性审计 (每月)                                             │
│                                                                  │
│  检测逻辑:                                                       │
│  · 找出所有 cosine_similarity > 0.92 的案例对                    │
│  · 如果两条案例的 verdict 相反 (一条 violation, 一条 compliant)   │
│  · → 标记为"存在争议"，推送合规团队裁定                          │
│  · 合规团队选择保留哪一条 verdict，另一条标记为 overruled         │
│                                                                  │
│  ⑤ 法条失效联动                                                  │
│                                                                  │
│  当法条标记为 deprecated 时:                                     │
│  · 查询: SELECT * FROM review_case                               │
│    WHERE law_references @> '[{"article_id": "被废止法条ID"}]'    │
│  · 匹配的案例标记为 law_deprecated                               │
│  · 这些案例在检索时权重 → × 0.3                                 │
│  · 通知合规团队: "以下案例引用的法条已失效，请确认是否仍有效"    │
└─────────────────────────────────────────────────────────────────┘
```

### 增强 7: 修订建议类型分层 (suggestion_type) [v2 新增]

**来源：Gemini 评估报告建议（必须补 3），v2 新增。**

**问题本质：** v1 的 `suggestion` 是自由文本字段，合同审查场景中存在三种截然不同的"建议"——纯提示、可直接粘贴的修订、需要谈判的协商要点。混在一起会导致法务和业务方困惑。

```
┌─────────────────────────────────────────────────────────────────┐
│  suggestion_type 三层分类                                        │
│                                                                  │
│  ① tip (纯提示)                                                 │
│  · 告知风险但不提供具体修改文本                                  │
│  · 适用场景: 措辞优化建议、格式建议、信息补充提醒                │
│  · 示例: "建议补充数据来源和截止日期"                            │
│  · UI 展示: 💡 淡蓝色卡片                                       │
│                                                                  │
│  ② revision (可直接采纳的修订)                                   │
│  · 提供可直接复制粘贴/一键接受的修改文本                         │
│  · 适用场景: 合规修改、格式修正、必备声明补充                    │
│  · 要求:                                                        │
│    · 修订文本必须是最小改动（minimal change principle）           │
│    · 修订前后做 diff 校验，确保只改了必要的部分                  │
│    · 修订不得引入新的合规风险（跨条款影响检查）                  │
│  · 示例:                                                        │
│    原文: "过去一年涨幅达35%"                                    │
│    修订: "截至2024年12月31日，该基金近一年收益率为35.2%，         │
│          同期业绩比较基准收益率为18.1%（数据来源：XX）。           │
│          基金过往业绩不代表未来表现。"                            │
│  · UI 展示: ✏️ 绿色卡片，带"接受修订"按钮                       │
│                                                                  │
│  ③ negotiation_point (谈判/协商要点)                             │
│  · 标识合同中需要与对方协商的条款风险点                          │
│  · 仅合同审查场景使用                                            │
│  · 适用场景: 权责不对等、条款偏向一方、异常免责、过高违约金      │
│  · 不提供"正确答案"（因为谈判没有唯一正确答案）                  │
│  · 提供: 风险说明 + 行业惯例参考 + 可能的协商方向                │
│  · 示例:                                                        │
│    "第8.3条违约金比例(30%)显著高于行业惯例(10-20%)。              │
│     建议与对方协商降低至合理区间，或增加违约金上限条款。          │
│     参考: 同行业标准合同模板中违约金通常为合同金额的10-15%。"     │
│  · UI 展示: ⚖️ 橙色卡片，带"标记为协商要点"按钮                │
│                                                                  │
│  数据存储:                                                       │
│  review_result.suggestion_type = tip | revision | negotiation    │
│  review_result.suggestion = 具体建议文本                         │
│                                                                  │
│  质量约束 (revision 类型):                                       │
│  · 修订 diff 行数不得超过原文的 50%（最小改动原则）              │
│  · 修订后文本不得包含快速过滤阶段的禁用词                        │
│  · 如果修订涉及金额/日期，必须与原合同其他条款保持一致           │
└─────────────────────────────────────────────────────────────────┘
```

## 三、设计取舍与未采纳建议

### 3.1 不做 Fine-tuning（沿用 v1 决策）

```
不采纳理由 (v1→v2 不变):
1. RAG 已经足够: 法规知识通过检索注入，不需要"记忆"在模型权重里
2. 更新困难: 法规频繁更新，微调模型无法及时跟进
3. 可审计性: RAG 模式每次审查的依据是明确的检索结果
4. 多模型灵活性: 当前设计可以随时切换底座模型
5. 成本: 每次法规更新都要重新微调，成本远高于更新知识库
```

### 3.2 不做"敏感度调节滑块"（沿用 v1 决策）

```
不采纳理由 (v1→v2 不变):
1. 合规是法律问题，不是概率问题。"违规"就是"违规"
2. 企业自定义宽松/严格标准通过自然语言规则精确描述
3. 已有的复核策略(全量/风险驱动/抽样)是"敏感度"的合理实现
```

### 3.3 Phase 1-2 不引入 Neo4j（v2 新决策）

```
v2 新增决策:
1. Neo4j 的核心价值在法条间的多跳关系推理，但 Phase 1-2 法条规模
   有限（200-500条），PG 递归 CTE 完全够用
2. 团队如果没有 Neo4j 运维经验，引入会带来 1-2 人月的意外成本
3. Phase 3 法条规模扩展到 3000+ 时再引入 Neo4j
4. PG → Neo4j 迁移路径: 通过 event-driven 双写，渐进迁移
```

### 3.4 不做"完全替换 Coze 工作流"（v2 新决策）

```
评估报告建议:
  "Coze 工作流里已经沉淀的 G1-G8 节点是团队的资产，
   新架构可以把 Coze 作为一种 LLM 后端接进来，而不是推倒重建"

v2 决策: 采纳。
  · Phase 1 允许 Coze 作为备选 LLM 后端之一
  · 通过 ModelRouter 将特定审查场景路由到 Coze 工作流
  · 渐进式迁移: 先用新架构处理营销材料，Coze 继续处理合同
  · Phase 2 合同审查能力成熟后，逐步替换 Coze 的合同审查节点
```

## 四、5 类审查卡片的架构设计理由

### 4.1 为什么需要 5 类卡片

```
┌─────────────────────────────────────────────────────────────────┐
│  5 类卡片的设计动机                                               │
│                                                                  │
│  核心矛盾:                                                       │
│  · v1 系统输出一个扁平的 issues 列表，混杂了错别字、禁用词、       │
│    缺失声明、法规违反、条款矛盾等完全不同性质的问题                │
│  · 审查员/复核员看到 30 条问题时，不知道从哪里开始                 │
│  · 不同问题的修复成本差异巨大（改个错别字 vs 重写条款）            │
│                                                                  │
│  设计原则:                                                       │
│  · 按"发现机制"分类，而不是按"严重程度"分类                       │
│  · 每类卡片有独立的技术实现路径（有的靠规则，有的靠 LLM）         │
│  · 卡片之间相互独立，可以独立开发、独立上线、独立关闭             │
│  · 用户可以按卡片过滤和优先处理                                   │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 各卡片的技术实现路径

| 卡片 | 名称 | 发现机制 | 是否需要 LLM | 适用文档类型 | MVP Phase |
|------|------|---------|-------------|-------------|-----------|
| ① | 文本基础核对 | 规则引擎（标点配对、错别字词典、数字格式） | 否 | 全部 | Phase 1 |
| ② | 红线与敏感词 | Aho-Corasick 自动机 | 否 | 全部 | Phase 1 |
| ③ | 形式与要素审查 | 合规自检清单 + 语义匹配 | 部分（语义匹配） | 全部 | Phase 1 |
| ④ | 语义与合规审查 | RAG + LLM（ACE 上下文 + 审查 prompt） | 是 | 全部 | Phase 1 |
| ⑤ | 逻辑与条款审查 | 条款图谱 + 跨条款一致性 Agent | 是 | 合同/长文档 | Phase 2 |

### 4.3 卡片的独立性保证

```
每张卡片在代码中是一个独立的 ReviewCardProcessor:

  public interface ReviewCardProcessor {
      int cardCategory();           // 1-5
      String cardTitle();           // 卡片名称
      boolean isApplicable(ReviewState state);  // 是否适用于当前文档
      List<ReviewResult> process(ReviewState state);  // 执行审查
  }

  @Component
  class TextBasicCheckProcessor implements ReviewCardProcessor {
      int cardCategory() { return 1; }
      String cardTitle() { return "文本基础核对"; }
      boolean isApplicable(ReviewState state) { return true; }  // 所有文档
      List<ReviewResult> process(ReviewState state) { ... }
  }

  @Component
  class ClauseLogicProcessor implements ReviewCardProcessor {
      int cardCategory() { return 5; }
      String cardTitle() { return "逻辑与条款审查"; }
      boolean isApplicable(ReviewState state) {
          return "contract".equals(state.getDocumentType());
      }
      List<ReviewResult> process(ReviewState state) { ... }
  }

  卡片的注册是声明式的:
  · 新增一种卡片 = 实现一个新的 ReviewCardProcessor
  · 卡片的启用/禁用 = isApplicable() 返回 true/false
  · 租户级定制 = 在 tenant_config 中配置哪些卡片启用
```

### 4.4 卡片间的依赖关系

```
卡片执行顺序:

  ① 文本基础核对  ──┐
  ② 红线与敏感词  ──┤── 并行执行（不依赖 LLM）
  ③ 形式与要素    ──┘
        │
        ▼ (完成后)
  ④ 语义与合规    ─── 依赖 ACE 上下文（需要 ③ 的缺失项作为 prompt 输入）
        │
        ▼ (完成后, 仅合同)
  ⑤ 逻辑与条款    ─── 依赖 ④ 的逐条款审查结果 + 条款图谱

  ①②③ 的结果会注入到 ④ 的 prompt 中:
  "系统已检测到以下基础问题，请在合规审查中同时关注:
   · 文本基础: 第3段存在2处标点错误
   · 敏感词: 第5段命中禁用词'稳赚不赔'
   · 缺失项: 未发现风险提示声明"
```
