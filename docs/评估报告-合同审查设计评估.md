# 智能合规审查系统 —— 合同审查方向适配评估报告

> 评估对象：`90-待整理/智能合规审查系统/` 文件夹内的全套设计文档（`00-overview` ~ `08-design-decisions`、`完整产品设计文档.md`）以及 `合同风险审查：现状与流程优化方案.doc`。
> 评估视角：这套设计若用于 **合同审查** 方向，合理性、可行性、理论上限，以及达到市面第一梯队水平所需的建设与持续优化周期。
> 编制时间：2026-04-17

---

## 零、前置定性（先声明一个关键事实）

阅读完所有文档后，必须在最开头指出一个会影响整个结论的事实：

| 文档类别 | 实际目标领域 |
| --- | --- |
| `00-overview` ~ `08-design-decisions` + 完整产品设计文档 | **金融营销物料合规审查**（基金销售管理办法、广告法）——内容对象是海报、推文、直播话术、说明书等对外宣传物料 |
| `合同风险审查：现状与流程优化方案.doc` | **合同智能审查**（`cheetah-module-contract` 工程）——审查对象是合同正文，关注条款风险、修订建议、书签定位、先进经验 |

两者虽然都叫"合规/审查"，但在**审查对象、问题模型、输出形态、精度要求、核心痛点**上是完全不同的两个系统。`00-08` 这套设计文档几乎所有具体例子都是"收益率20%、保本暗示、风险提示字号"之类营销话术违规——它并不是为合同审查而写的。

本报告的评估因此分为两层：

- **A 层**：这套设计本身（作为一个面向营销物料的 LLM+RAG+ACE 审查系统）是否合理、可行、上限多高。
- **B 层**：如果把这套设计**迁移/适配到合同审查**（用户真正关心的方向），是否合理、需要改动多少、能否对标第一梯队。

两层都会给出结论。用户若在意的仅是合同审查方向，请直接看 B 层。

## 一、总体判分

| 维度 | A 层（营销物料审查） | B 层（合同审查迁移） |
| --- | --- | --- |
| 架构合理性 | **A-**（主流范式、考虑到位） | **B**（思路对，但合同特有的核心能力缺失） |
| 工程可行性 | **A-**（技术栈成熟、落地路径清晰） | **B-**（能落地但需补齐 30%~40% 的关键能力） |

| 理论上限 | 准确率 **90%~95%**、对标国内一梯队 | 准确率 **80%~88%**，距离 Harvey/幂律一梯队有明显差距 |

> **作为一套"金融营销物料合规审查"的系统设计，它处在主流合理水平，落地可以做到国内一梯队。但作为"合同审查"的方案，它只解决了合同审查的 1/2 问题——把它直接照搬到 `cheetah-module-contract` 的场景，会再次命中 .doc 文件里已经罗列的那些客户投诉（修订建议不可采纳、定位对不上、字段太多、幻觉），无法达到第一梯队（Harvey、Ironclad、幂律 MegaLaw、法小信那一档）。**

## 二、A 层评估：作为"营销物料合规审查"系统

### 2.1 设计合理性——符合当前工业界主流范式

这套设计在 **"2024~2026 年 RAG-centric 合规系统"** 的范式上站得很稳。几个关键判断：

1. **"LLM 读法律 + 人只做确认"** 的取舍是对的。几百部金融法规、几千条法条，无论走 Drools 还是正则都维护不下来；用 LLM 结构化 + 人工 review & approve，是目前能把"知识工程"摊到可接受成本内的唯一路径（Kira、Harvey、幂律都是这个思路）。
2. **四路混合检索（向量 + 结构化 + BM25 + 知识图谱）+ RRF 融合** 是业界事实标准。很多"演示级"项目只做向量检索就交付，这套设计能认识到"纯向量检索排名会被'收益率'这种精确术语稀释"——这个认知在工业界已经算"成熟团队"水平。
3. **多粒度 Embedding**（法条原文 / 行为描述 / 违规示例 / 语义延伸各自独立向量化）符合 RAG 最新实践，对召回率有实质提升；相当于给每条法条生成"多面人设"的语义锚点，比单粒度检索在边界案例上会有 5~10 个百分点的召回提升。
4. **"法条锚点验证 —— LLM 只输出 ID，系统回填原文"**（`08-design-decisions` 增强 2）是**整套设计里最有价值的单点**。这一条直接消除了法条内容被幻觉的概率，国内真正落地防幻觉的系统里做到这一步的并不多。
5. **两级风险评分**（issue 级 + task 级）、**三级引用校验**（精确 / 模糊 / 幻觉标记）、**按学习价值分沉淀案例**、**黄金测试集回归**——这些都是在处理 LLM 审查实际落地时真正会踩到的坑，说明设计者走过比较完整的迭代链路或做过充分的 prior art 研究。
6. **ACE（Agentic Context Engineering）+ RRF + 效力层级重排** 的组合把"上下文动态组装"的主流做法做得很完整，在学术侧也在 arXiv 2024~2025 一批 agent RAG 论文里能找到 counterpart。

### 2.2 设计中存在的 A 层风险

虽然合理，但有几处结论下得太乐观或落地风险被低估：

#### R1. "5 路检索，200~500ms" 的延迟预算乐观

- Milvus 的 top_k=10 向量检索 + `bge-large-zh-v1.5` Embedding 模型（1024 维）本地推理，单次查询本身就 30~80ms；
- 一次审查要对**每个分段**做一次向量检索，长文档分 10 段就要 10 次 Embedding + 10 次 Milvus 查询；
- ES + PG 并行没问题，但图谱查询（Neo4j Cypher）在有复杂路径的场景会到 100~300ms；
- **真实的 p95 检索延迟应该按 600~1500ms 规划**，而不是 500ms 封顶。
- 结论：延迟预算应被重排为"5 路检索 p50 < 600ms / p95 < 1500ms"。

#### R2. LLM 审查一次 15~20K tokens 的上下文，成本与延迟都偏高

- GPT-4o 输入 ~$2.50 / 1M tokens + 输出 ~$10 / 1M tokens；按每次审查 15K input + 3K output，**单次审查成本 ≈ $0.067**；
- 按 100 QPS 规模跑一年，**仅 LLM 调用成本就约 200 万美金**，对中型企业不可忽视；
- 延迟侧，15K tokens input 的 GPT-4o 首字节响应就要 2~4s，加上生成阶段稳定在 8~15s；"短内容 < 10s"在大部分场景下不可达。
- 结论：设计需要引入 **Prompt Caching（Anthropic / OpenAI 都支持）**、**小模型路由（简单内容用 4o-mini，复杂内容用 4o/Sonnet）**、**法条上下文 KV 缓存**，否则生产成本与性能都会爆。这些在现有设计中**完全没有提**。

#### R3. "越用越准"的闭环存在退化风险

- 人工复核员如果偏向"简单地 Confirm"，案例库会被大量冗余 confirmed 案例污染，检索 top_k 时真正高价值的 rejected/supplemented 案例可能被挤出；
- 同一类违规在不同复核员之间尺度不一致（这在合规审核现实中非常常见），沉淀的案例会互相打架；
- `08-design-decisions` 提了黄金测试集，但没有设计**案例淘汰机制**（e.g. "同一 embedding 邻域下 confirmed 案例过多时，按时间衰减或相关性分层抽样"），长期会 bloat。
- 结论：闭环是"应然的正循环"，但落地时很容易变成"噪声叠加环"。需要补充**案例生命周期管理**。

#### R4. Token 预算的"按相关度得分裁剪"在实际会把关键法条裁掉

- RRF 分数高 ≠ 覆盖面广。比如某段文本同时触发"预期收益承诺"和"信息披露不完整"两个违规，如果检索出的法条里前者 RRF 分很集中，后者分散，裁剪后很可能把后者的相关法条全裁掉；
- 正确做法是**按违规类别分桶（bucket by norm_type）后再裁**，即每个类别至少保留 top-N，而不是全局 top-K。
- 现有设计只做了全局裁剪。

#### R5. 长文档"三智能体"方案过于简略

- `08-design-decisions` 的增强 3 把长文档拆成 "分段专家 + 摘要专家 + 终审专家"，但没有定义：
  - 三者之间的消息协议（摘要给终审的是什么结构）；
  - 终审专家如果发现矛盾，是改写分段结果还是标记冲突？
  - 10 个 chunk 并行的顺序依赖（段落 5 的结论可能依赖段落 3 的上下文）；
- 真正需要的是 **StateGraph / LangGraph / LlamaIndex Workflow** 这类显式编排，而不是 "agent 名字列三个"。

### 2.3 A 层理论上限

在"有 50~100 人运营团队 + 24 个月持续优化 + GPT-4o/Claude Sonnet 级别模型"的假设下：

| 指标 | 冷启动（MVP 上线） | 12 个月 | 24 个月 | 36 个月 |
| --- | --- | --- | --- | --- |
| 违规召回率 | 75~82% | 87~90% | 91~94% | 93~96% |
| 违规精确率 | 70~80% | 83~88% | 88~92% | 90~95% |
| 法条引用正确率（采纳 ID 回填后） | ≈ 100% | ≈ 100% | ≈ 100% | ≈ 100% |
| 人工复核承载率（系统判定可直接通过） | 20~30% | 50~65% | 70~80% | 80~88% |

结论：**A 层场景下，这套设计的理论上限确实能达到国内一梯队（幂律、通联、蚂蚁 CLAIM 等）在营销物料侧的水平**——前提是把 R1~R5 这几个坑填好。

## 三、B 层评估：迁移/适配到合同审查

### 3.1 场景差异（为什么不能直接套用）

先把两个领域的关键差异摆出来，这是评估 B 层的基础：

| 维度 | 营销物料审查（00~08 设计目标） | 合同审查（用户真实业务） |
| --- | --- | --- |
| 审查对象 | 短文本/图片/说明书摘要，通常 < 5000 字 | 合同全文，通常 5000~50000 字，长合同 10 万字 |
| 违规类型 | 点状违规（某一句话）、缺失元素（缺风险提示） | **条款级**违规、**跨条款**逻辑矛盾、**权责不对等**、**合同空白/不一致**、**隐藏风险条款** |
| 法条依据 | 广告法、基金销售办法等，<500 条核心条款 | 民法典、合同法原理、行业合同惯例、内部合同模板、监管红线——几乎无穷 |
| 输出形态 | 违规点 + 原因 + 建议 | **必须给出可直接粘贴/替换的修订正文** + **精确到字符 span 的书签定位** + **与 OnlyOffice/Eagle 的联动** |
| 客户采纳标准 | 合规官判断 OK 即可 | 法务/业务双方都要认"可采纳"；错一个字符的定位都会被吐槽"Agent 不行" |
| 主要失败模式 | 漏检、过度审查 | **修订建议不可执行**、**定位对不上**、**条款关联被遗漏**、**跨段矛盾被无视** |
| 知识库规模 | 500~2000 条法条足以 | 需要覆盖：法条 + 行业标准合同模板库 + 历史审过的合同案例 + 内部审查经验（"先进经验"） |

.doc 文件里用户团队自己总结的 5 类核心问题（5.1~5.6），**有 4 类在 00-08 设计里完全没有被专门处理**：

| .doc 中的痛点 | 00-08 设计是否处理 |
| --- | --- |
| 5.1 单条字段过多导致幻觉 | **未处理**（设计里一条 issue 仍有 5+ 字段） |
| 5.2 审查+定位+代写修订绑得过紧 | **未处理**（没有拆分 Agent） |
| 5.3 通用与先进经验双写 | 不适用（无此概念） |
| 5.4 JSON 修复链路过长 | 部分处理（BeanOutputConverter + 重试） |
| 5.5 缓存与定位顺序 | **未处理** |
| 5.6 页面不支持修改审查内容 | **未处理**（设计侧重 confirm/reject/modify，但没给合同修订回填链路） |

### 3.2 迁移到合同审查时必须补齐的能力

按重要性排序（每项后面给出在现有 00-08 设计里的缺失程度）：

#### 必须补 1：精准字符级定位（书签 / locationId / span）

- 合同审查产品的用户体验第一杠杆：点击"第 23 条权责不对等"要能在 Word/OnlyOffice 里精准高亮那一句话；
- 现有设计只有"段落索引"（segment_index），**根本不足以支撑合同审查**；
- 必须补：
  - 字符 span 提取（LLM 输出 `location: exact substring` + 后端做严格子串校验，失败则降级为"段落级高亮"）；
  - 与 Word/OnlyOffice 的书签双向同步；
  - 合同修订后的 span 漂移处理（re-anchoring）。
- 缺失度：**80%**。`.doc` 5.1、5.2 都在讲这个。

#### 必须补 2：条款级建模 + 跨条款关联分析

- 合同的"条款"是语义单位，不是段落。条款间的引用（"依照本合同第 8.3 条规定")、定义（"本合同所称'关联方'指……"）、权利义务对称性（"甲方有权……但乙方无相应救济")——这些**必须用图结构或条款表建模**；
- 设计里的 Neo4j 是法条间的知识图谱，不是**合同内部条款图谱**；
- 必须补：
  - 合同解析器（不是简单分段，而是识别"第 X 条 Y 款 Z 项"层级）；
  - 合同内条款图谱（定义条款、引用条款、生效条款、违约条款）；
  - 跨条款一致性 Agent（检测权责是否对称、争议解决是否自洽、生效与终止条款是否矛盾）。
- 缺失度：**90%**。这是合同审查与营销审查**最本质的差异**，现有设计完全没触及。

#### 必须补 3：修订建议的"可采纳性"约束

- 合同场景的 KPI 不是"是否发现风险"，而是"**客户直接 Ctrl+C/V 能否用**"；
- 需要：
  - 按 `suggestion_type` 分层（纯提示 / 可采纳修订 / 协商点建议）——这个 .doc 7.1 已经建议了；
  - 修订建议与原条款的 diff 校验（只允许最小改动或明确标注"重写本段"）；
  - 修订后的条款不得与合同其他条款产生新矛盾（回到必须补 2）。
- 现有设计的 `suggestion` 是一个自由文本字段，没有这一层。
- 缺失度：**85%**。

#### 必须补 4：合同类型差异化

- 销售合同 / 采购合同 / 服务合同 / 股权合同 / 劳动合同 / 保密协议……每种合同的必备条款、风险重点、行业惯例都不同；
- 现有设计只有"内容类型 / 产品类型"两维，语义上跟合同类型对应不起来；
- 缺失度：**70%**。

#### 必须补 5：大模型协同的显式编排（StateGraph）

- 合同审查的一次完整审查往往是：
  `分类 → 条款解析 → 定义抽取 → 逐条风险审查 → 跨条款一致性检查 → 修订建议生成 → 终审汇总`
- 每一步都是独立 Agent，存在状态依赖和条件分支；
- 现有设计的"三智能体协作"只是一句话带过，根本不足以支撑合同审查的复杂编排；
- 必须引入 LangGraph / Spring AI Advisors + WorkflowEngine / 自研 DAG 编排器。
- 缺失度：**75%**。

#### 必须补 6：内置"标准合同模板库"作为知识底座

- Harvey / 幂律 / Ironclad 的核心壁垒之一：预置数千份行业标准合同模板（采购、NDA、SaaS 服务、劳务、股权），并且每份都做过条款级标注；
- 审查时做"与最相近标准模板的条款级 diff"——这是比"向量检索法条"**更有用**的能力；
- 现有设计完全没有"模板合同库"这个概念。
- 缺失度：**100%**。

#### 必须补 7：审查结果的人工编辑 + 回写持久化

- .doc 5.6 专门提到，当前合同审查卡片是只读的，用户无法 confirm/reject/修正；
- 05-feedback-loop 的 confirm/reject/modify/supplement 设计**本身是对的**，但没有定义与合同正文修订的联动（合同改了一条，原有 AI 标注要不要作废？要不要重跑？）；
- 缺失度：**60%**（基础在，但合同场景联动未定义）。

### 3.3 B 层的上限估计

| **Spellbook** | Word 原生集成，修订建议可直接接受，小团队也能用 |
| **幂律 MegaLaw** | 国内第一梯队，合同审查 + 法律大模型，关键条款识别 90%+ |
| **通联 / 法小信** | 国内次梯队偏上，80~88% 关键条款识别 |

**结论**：

> 照搬 00-08 设计到合同审查，可以做到"**次梯队偏上**"的水平（约 80~88% 的条款级召回，50~70% 的修订可采纳率），大致与目前用户团队 `cheetah-module-contract` 现状或略优的水平，**无法达到 Harvey/幂律这一档第一梯队**。
> 要达到第一梯队，必须在现有架构之上**再做大改**：补模板库（必须补 6）、补条款图谱（必须补 2）、补字符级定位（必须补 1）、补 Agent 编排（必须补 5），这三点共同构成**合同审查的"第一梯队门槛"**，而不是"锦上添花"。

### 3.4 与用户现状（.doc）的关系

`.doc` 里反映的 Coze 工作流 + 三条审查线（自定义 / 通用 / 先进经验）+ 书签定位 + 字段幻觉，**本质上已经在做合同审查**；现有问题是：

- 字段太多 → 幻觉重；
- 修订建议与纯提示混淆 → 不可采纳；
- 定位对不上 → 信任塌方；
- 只读卡片 → 无法闭环反馈。

如果直接把 00-08 的设计替换掉 Coze 工作流，会发现：

- **能带来的改进**：混合检索 + RRF + 法条 ID 回填 + 多粒度 Embedding + 自定义规则接入 + ACE 动态组装 ➜ **对"有没有命中法条"类问题有实质改进**；
- **不能带来的改进**：定位精度、修订可采纳性、条款间一致性、合同模板对标 ➜ **.doc 里反映的客户不满不会消失**。

换句话说：**这套设计能解决 .doc 5.1 的"字段过多"的一半问题（通过法条 ID 回填减少法条幻觉），但 5.2~5.6 几乎都要另外投入做**。

### 4.3 MVP 切入风险

设计里 `07` 章节 MVP 阶段划分合理：Phase 1 核心链路 → Phase 2 反馈闭环 → Phase 3 知识自动化 → Phase 4 企业级。但有几点提醒：

1. **Phase 1 要求"手动导入 50~100 条核心法条"** —— 对营销物料够，对合同审查太少，应至少 500 条 + 200 份合同模板；
2. **Phase 1 建议增加黄金测试集** —— 否则后面迭代的准确率变化是盲的；`08` 的黄金测试集设计需要提前到 Phase 1；
3. **Phase 2 做案例沉淀前应先完成 Manual RAG Test** —— `08` 提到的手动 50 样本验证，强烈建议作为 Phase 0（编码前 2 周）；
4. **Phase 3 的爬虫合规风险被低估** —— 证监会、银保监会官网的内容爬取需要确认合规边界，大厂通常采购北大法宝 / 威科先行的 API 而不是自建爬虫。

## 六、关键建议（若决定推进）

按 ROI 从高到低：

1. **立即做 Manual RAG Test**：在写任何代码前，拿 50 份真实合同 + 50 条核心法条，手工跑一轮 GPT-4o 审查，记录召回率、定位准确率、修订可采纳率。这是 `08-design-decisions` 附录里已经建议的，但强烈建议提前到整个项目的 Day 1。**成本：2 个人 2 周**；**收益：能否验证整个架构假设**。

2. **把"字符级定位 + 条款图谱"前置到 MVP**：这是合同审查与营销审查的最大差异，也是 .doc 里客户投诉的根源。在 Phase 1 就引入会比 Phase 3 再补省 30% 时间。

3. **采纳 08 的 5 项增强全部落地**，但增加两条：
   - **(6) 案例淘汰机制**：按时间衰减 + 同 embedding 邻域抽样防止 bloat；
   - **(7) 修订建议按 suggestion_type 分层约束**：纯提示 / 可采纳修订 / 协商点 三选一，与 .doc 的 7.1 呼应。

4. **不要在 Phase 1 碰 Neo4j**：先用 PG 的递归 CTE 和 JSONB 表达法条/条款关系，等规模上来后再迁移 Neo4j。团队如果没有 Neo4j 运维经验，引入它会带来 1~2 人月的意外成本。

5. **Prompt Caching 和模型路由必须在 Phase 1 就设计进去**：不做这一步，上线后第 3 个月 LLM 账单会成为团队生存压力。

6. **黄金测试集建设**：100 条合同、200 条法条、500 条案例，由至少 3 位资深合规官独立评审取共识，作为所有迭代的唯一评估基准。这套东西的价值 ≈ 整个架构。

7. **放弃"100% 替换 Coze 工作流"的执念**：Coze 工作流里已经沉淀的 G1~G8 节点是 .doc 团队的资产，新架构可以把 Coze 作为一种 LLM 后端接进来，而不是推倒重建。

## 七、最终结论

### 对"这套设计是否合理"：

> **是合理的**，架构选型在 2025~2026 年的业界视角下处在主流合理水平，没有明显错误的技术决策，防幻觉、多粒度检索、ACE 动态组装、反馈闭环都是高质量的工程判断。
> 但**合理 ≠ 完备**。设计里有 5 个隐性坑（延迟预算、LLM 成本、案例退化、token 裁剪粒度、Agent 编排简略），上线前必须补。

### 对"是否具有可行性"：

> **可行性没问题**，技术栈全部是成熟组件，没有黑科技依赖，没有需要突破的科研问题。**风险在于人力规模和持续运营**（12~18 人团队起步，合规专家 2~5 人），而不是技术本身。

### 对"上限能有多高"：

> - 用于**营销物料合规审查**：理论上限能到**国内一梯队**（幂律、通联同档），准确率 90~95%，36 个月内可达；
> - 用于**合同审查**（用户真实业务）：理论上限是**国内次梯队偏上**（~85%，接近法小信、法狗狗），**无法直接对标 Harvey / Spellbook / Ironclad / 幂律 MegaLaw 这一档第一梯队**。要达到第一梯队，必须在现有架构之上再补"字符级定位、条款图谱、多 Agent 编排、合同模板库"四项核心能力，这四项的代码量和团队复杂度**约等于再做一套 00-08**。

### 对"需要多久的建设和持续优化时间"：

> - 营销物料方向：MVP **6~9 个月**，一梯队水平 **25~36 个月**；
> - 合同审查方向：MVP **12~15 个月**，次梯队头部 **24 个月**，一梯队水平 **36~48 个月**，且需要 15~22 人团队 + 持续 2~3 年的数据积累和反馈优化。

### 一句话总结

> **架构主流、思路清楚、落地可行；用于营销物料能进一梯队，用于合同审查只能进次梯队——除非再做一层合同专属的条款图谱 + Agent 编排 + 模板库工程，那将是比当前设计更大的一笔投入。**
